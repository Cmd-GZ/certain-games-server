# 区域裁决设计（I3 的 C 类：伤害 / 交互 / 方块 / 移动）

> 状态：**C0 已落地（2026-11-04，MiniGameLib 1.26.0 + HillKing 1.9.0 试点）**，C1~C4 未开始。这份文档先定"分发规则长什么样"，
> 目的是让剩下那 200 个 `@EventHandler` 能**机械地**搬，而不是每个游戏各想一套。
>
> 前置：A 类（生命周期 + 环境）已在 `com.hub.session.SessionEvents` 收口，见 `docs/框架不变量.md` I3 节。

---

## 1. 要解决的问题

A 类做完之后，游戏模块里还剩 **260 个 `@EventHandler`**，绝大多数是这几类：

| 事件 | 数量 | 现在每个游戏各自写的逻辑 |
| --- | --- | --- |
| `PlayerInteractEvent` | ~26 | 右键自家道具 → 开菜单 / 退出 / 开始 |
| `EntityDamageEvent` / `ByEntity` | ~36 | 局内无伤 / 只允许某种武器 / 击退 |
| `BlockBreakEvent` / `BlockPlaceEvent` | ~30 | 自家场地内禁改，场地外不管 |
| `PlayerMoveEvent` | ~20 | 掉下去 / 进球 / 到达检查点 |
| 其它（拾取、投掷物、传送、命令预处理…） | ~150 | 各家自己的规则 |

它们的共同毛病：**判断条件全是"这个玩家/这块方块是不是我的"**，而"是不是我的"这件事，
框架其实**已经知道**（I2 的区域注册表 + I1 的归属链）。每个游戏自己再判断一遍，
就有了 26 份互不相同的、优先级各异、其中 43% 挤在 `HIGHEST` 的判断。

**这就是 C 类要收口的东西**：让"这块地归谁"由框架算一次，事件只发给**归属者**。

---

## 2. 分发规则（核心）

一条事件 `e` 的归属者按下面的顺序判定，**先命中先算**：

```
1. 有玩家参与时：该玩家归属链的**叶子会话**（最深的那层）
      —— 与 A 类一致（派对 ⊃ 小游戏 时，叶子是小游戏）
2. 无玩家参与时（爆炸、投掷物、实体伤害）：按**发生位置**查 I2 区域注册表，
      取包含该位置的那一块区域 → 它的归属者
3. 都不命中：归"公共区"，用 HubCore 的世界规则（现有 `GameWorlds` 的 pvp / build 开关）
```

**只有归属者被调用一次**。别的游戏**不会**收到这条事件 —— 这是 I3 的"裁决唯一"。

### 2.1 为什么玩家优先于位置

真实事故（`docs/框架不变量.md` I3 节记的那两条）：

- SkyPit 的守卫"只要双方不在天坑就取消"，结果打掉了 `world_duel` 的 `pvp: true`；
- GuessTheBuild 在 `HIGHEST` 无条件取消**所有世界**的爆炸，导致单挑的风弹推不动人。

两次都是"**位置判断写成了全局判断**"。以玩家归属优先，能让"人在别人场地里"这种边缘情况
也跟着他真正所属的那一局走，而不是跟着脚下那块地走。

### 2.2 位置兜底是必要的

爆炸、火焰蔓延、掉落的箭——这些事件里**没有玩家**可以查归属，只能看位置。
所以 I2 的区域注册表（`ArenaRegion` / `RegionRegistry`）是 C 类的前置条件：
**没声明区域的游戏，C 类事件永远落到"公共区"**。这也是为什么 I2 的落地进度要一起看。

## 3. API 草案

### 3.1 游戏侧：声明"这块地上发生什么我说了算"

```java
final class SkyPitSession extends GameSession {
    SkyPitSession(...) {
        // 只关心"自己区域内的伤害"，别的一概不表态
        arbiter().on(EventKind.DAMAGE, (ctx) -> {
            if (ctx.isBetweenPlayers() && !pit().allows(ctx)) {
                ctx.cancel();          // 我说了算：取消
            }
            // 不表态 = 放行
        });
        arbiter().on(EventKind.BLOCK_BREAK, (ctx) -> ctx.cancel());
    }
}
```

- `arbiter()` 挂在会话上，会话 `end` 时**自动注销**（和 `ownTask` 一样，不用手动清理）；
- `ctx` 里给的是**语义**，不是 Bukkit 事件：`who / whom / block / kind`，避免游戏再去 `instanceof`；
- 一个 `EventKind` **一个回调**：重复注册直接抛异常（I5 精神：非法状态不要静默）。

### 3.2 框架侧：唯一的分发者

```java
public final class RegionEvents implements Listener {     // 由 MiniGameLib 注册一次
    @EventHandler(priority = EventPriority.LOWEST)
    public void onDamage(EntityDamageEvent e) {
        GameSession owner = ownerOf(e);          // 见 §2 的三步判定
        if (owner == null) return;               // 公共区：交给 GameWorlds 的世界规则
        owner.arbiter().fire(EventKind.DAMAGE, Context.of(e));
    }
}
```

- **`LOWEST`**：抢在所有游戏现存的处理器前面。这样"框架放行、游戏却取消"的情况
  在迁移过程中会**暴露成 bug**（游戏要么迁走、要么显式声明），而不是被顺序掩盖。
- 迁移期允许游戏保留旧处理器（幂等取消无害），但**一个事件类型要么全迁、要么全不迁**，
  否则会出现"框架放行 + 游戏 HIGHEST 取消"的混合态，排查很痛。

### 3.3 公共区的默认值

**保持现状**（世界规则说了算），**不做**"默认拒绝、显式允许"的大翻转。

`框架不变量.md` 原来说的是"默认拒绝"，但那是**目标态**。现在直接翻会一夜之间禁掉
所有建造、所有 PvP、所有交互（200 个处理器里有一半是靠"默认放行"工作的）。
所以本草案把它降级成**分阶段目标**：先做到"归属者唯一"，等 C 类迁完再讨论默认值。

## 4. 迁移顺序（风险从低到高）

| 批 | 内容 | 为什么这个顺序 |
| --- | --- | --- |
| **C0** | 框架：`EventKind` / `Context` / `SessionArbiter` / `RegionEvents` + **SkyPit 的伤害裁决**试点 | SkyPit 是唯一被记录在案的真实事故，且它是 D26 单区域，最容易看出对错 |
| **C1** | `BlockBreak` / `BlockPlace`（~30 个）：几乎全是"自家场地内禁改" | 纯取消、无玩法风险，且改错立刻能看出来（能拆了/拆不了） |
| **C2** | `PlayerInteract`（~26 个）：自家 GUI | 只影响自己（B 类），和 C 类用同一套 API 顺手做 |
| **C3** | `EntityDamage` / `ByEntity`（~36 个） | 玩法风险最高：PvP / 无伤 / 击退 / 淘汰判定都在这里 |
| **C4** | `PlayerMove`（~20 个）+ 其它零散（拾取、投掷物、命令预处理） | 每 tick 跑，性能要单独看（`RegionRegistry` 查表必须 O(1) 或按 chunk 分桶） |

每批的要求和 A 类一样：**一次一个游戏、一局一验**，回归脚本用
`.server/regress-a.sh`（会话 / 钩子 / 收房 三列都要绿）。

## 5. 已知风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| **事件顺序变化** | 游戏原来在 `HIGHEST` 取消，迁到框架 `LOWEST` 后，中间优先级的插件会看到"未取消"的状态 | 迁移**一个事件类型一次性完成**；冒烟里专门验"该取消的确实取消了" |
| **`PlayerMove` 性能** | 每 tick 每个玩家都触发，若每次线性扫区域表会拖慢主线程 | 区域表按"世界 + chunk"分桶；只在**跨 chunk** 时重算归属（缓存到玩家身上） |
| **区域没声明** | 没声明的游戏，事件落到公共区 → 表现为"以前能取消，现在不取消了" | 迁移前先确认该游戏的 `[区域]` 已在 doctor 里出现（I2 已 20 个游戏 / 25 块） |
| **语义丢失** | `ctx` 只给语义字段，游戏要的细节可能在事件对象里 | `ctx.raw()` 留给"确实需要"的地方，但**每用一次都要在注释里说清为什么** |
| **回滚** | 万一某游戏迁坏 | 框架侧只**分发**不做判断，回滚 = 把该游戏的 `arbiter()` 声明去掉 + 恢复旧处理器，两步都在一个文件里 |

## 6. 和 A 类的关系（为什么先做 A 类是对的）

A 类给 C 类铺了三块地基，省了很多返工：

1. **`SessionEvents` 已经证明"单一监听器 + 语义回调"这条路走得通**（22 个游戏、都有实测）；
2. **会话生命周期决定了 arbiter 的注册/注销时机** —— 不用再发明一套"什么时候算在局内"；
3. **`rules()` 已经吃掉"环境类"那一半**，C 类不用再管饥饿/掉落这种"全有全无"的规则。

---

## 7. 什么时候可以宣布 I3 完成

三个条件，缺一不可：

1. `grep -r '@EventHandler' 游戏模块` 的结果只剩**已登记的例外**（当前 4 个：SkyPit / GTB / 派对 / Quark，见不变量 I3 节）；
2. C3（伤害）迁移完成并**实测过一局 PvP**（DuelArena 或 KnockbackBattle）与**一局无伤游戏**（HillKing）；
3. 公共区默认值那个问题有结论（保持现状 or 翻转），并写进不变量。

## 8. 怎么验（C 类必须能"看见"裁决结果）

A 类靠"房间销毁 + 已通知"就够，C 类不行 —— **必须真的触发那个事件**。
假玩家不能互相打，但**控制台可以制造事件、也可以读结果**：

```text
# 制造伤害（Paper 自带管理命令）
damage Beta 5
damage Beta 5 minecraft:player_attack

# 读结果（输出进控制台日志，冒烟可以断言）
data get entity Beta Health
```

判据举例（HillKing 试点：场内无伤）：

| 场景 | `data get … Health` |
| --- | --- |
| 在局内被 `damage` 打 | **20.0f**（框架裁决取消，没掉血） |
| 在主城被 `damage` 打 | < 20.0f（公共区放行，正常掉血） |

方块类同理：控制台 `setblock` 看不出"玩家能不能挖"，得让假玩家真正破坏方块 ——
这条暂时没有工具支持，**C1 之前要先补一个"假玩家破坏方块"的动作**（`fakeclient` 现在只会发命令）。
