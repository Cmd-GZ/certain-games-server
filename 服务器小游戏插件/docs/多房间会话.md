# 多房间会话（D22 后半）——迁移手册

> 状态：**未开始**（框架原语已就绪，见 §2）。目标：**同一个游戏同时开多个房间时不串台**。
> 前置：`docs/框架不变量.md` 的 I1（归属链）、D2（每游戏最多 8 房间）、D22（按多份状态建模，键是房间 id）。

## 1. 现在为什么不能多房间

| 层 | 现状 | 后果 |
| --- | --- | --- |
| `RoomContext.BY_GAME` | **每个游戏一个槽**，`/hub join` 时后者覆盖前者 | 同游戏两个房间时，游戏只认最后绑定的那个 |
| 游戏的 `Map<String, XSession> sessions` | 键是**场地名**（arenaName） | 两个房间若用同一张地图（场地名相同）→ **共用同一个会话**：队列、计分、倒计时全混在一起 |
| `arenaOf(uuid)` | 返回场地名 | 同上：两个房间的玩家竞技场名一样，游戏侧分不开 |

框架已经能区分"**谁进了哪个房间**"（`RoomContext.roomOfPlayer`），只是没有任何游戏用它来分桶。

## 2. 框架已备好的原语（`MiniGameLib 1.33.1`）

```java
// 玩家进房间时框架已记好；下线时自动清理
UUID id = player.getUniqueId();
String key = RoomContext.sessionKeyFor(id, gameKey, arenaName);
//   = 房间 id（有记录）   否则 = 场地名（老路径，行为不变）
```

另有：`roomIdOfPlayer(id)` / `roomOfPlayer(id)` / `clearPlayer(id)`；
若同一游戏被两个房间同时使用，`bind()` 会打**警告**（不静默）。

## 3. 迁移一个游戏的标准步骤

以任意 `XxxManager` 为例（**一次只做一个游戏**）：

1. **建会话处**加键解析
   ```java
   private XxxSession ensureSession(Player p, String arenaName) {
       String key = com.hub.room.RoomContext.sessionKeyFor(p.getUniqueId(), GAME_KEY, arenaName);
       ...sessions.computeIfAbsent(key, k -> new XxxSession(this, arenaName));
   }
   ```
   ⚠️ 会话的 `super(gameKey, arenaName)` 里那个 **arenaName 保持不变**（它是"哪张地图"，
   而 `sessions` 的键才是"哪个房间"）。两者语义不同，不要合并。

2. **取会话处**全部改成"先求键再取"
   - `sessions.get(arenaName)` → `sessions.get(keyOf(player, arenaName))`
   - `sessionFor(arenaName)`（按场地找会话）→ 改成按玩家找：
     `sessionOf(player)`，实现是 `sessions.get(RoomContext.sessionKeyFor(...))`
   - 遍历所有会话的地方（广播、tick、doctor）保持遍历 `sessions.values()` 即可

3. **`arenaOf(uuid)`**：如果游戏用它区分"玩家在哪一局"，也要跟着改成"房间 id 优先"，
   否则两个房间同名场地仍会互相看到。**优先做法**：加一个 `sessionOf(player)`，
   让"取玩家那一局"统一走会话，不再靠场地名。

4. **验证**（缺一不可）
   - `tools/build.sh --deploy` 绿
   - 单房间回归：`.server/regress-a.sh` 该游戏五列全绿（**行为必须和迁移前一致**）
   - **多房间回归**：同一游戏建两个房间（建议**同一张地图**，才逼出串台），
     两个假玩家各进一个，断言：
     ```
     [对局] 2 个活动对局：{<game>=2}          ← 两个会话
     [归属] 2 人有归属
     ```
     再让 A 房间跑完一局，确认 B 房间的等待队列/场地没有被清空。

## 4. 建议迁移顺序（风险从低到高）

| 批 | 游戏 | 理由 |
| --- | --- | --- |
| 1 | **MemoryFlip / LuckyPillar / TntRun / OneShot** | 单图或键简单、逻辑短，最好验 |
| 2 | DigToBottom / FootballArena / JumpFill / LandClaim | 多场地但键统一 |
| 3 | HillKing / SnakeParty / GroupRace / KnockbackBattle / HotPotato / AnvilBattle / AnimalSlaughter / ArrowRain / FireJumper / BuildRun / DuelArena / MurderMystery / TNTBattle / SkyPit | 逻辑重的放后面 |
| 4 | **ArcadeParty** | 派对是"编排器"，它的房间就是派对房间；要和 D17 `PARTY_MULTI` 一起想 |

## 4.5 ⚠️ 一个必须先想清的前提：**场地对象也要按房间分**

写这份手册时又核了一遍代码，发现**只换会话键不够**：

- 很多 manager 不只 `Map<场地名, Session>`，还有 `Map<场地名, XxxArena>`（场地对象：状态、玩家集合、计分板）；
- 两个房间**用同一张地图**时，场地名相同 → **两个房间共用同一个 Arena 对象** → 玩家集合、状态机、
  计时器全部撞在一起。换会话键只能分开"会话"，分不开"场地"。

所以 D22 后半的**正确顺序**是每游戏两步：

1. **场地按房间分**：`Map<房间 id, XxxArena>`（房间 id 从 `RoomContext.roomIdOfPlayer` 取），
   或让 Arena 变成"每个房间一份的运行时对象"（配置里的坐标仍是模板坐标，读时用 `RoomBinding.apply`）；
2. **会话按房间分**：`Map<房间 id, XxxSession>`（本手册 §3 的步骤）。

**单图游戏也不能例外**：MemoryFlip 的 `arenaKey()` 直接返回 `"main"` —— 两个房间必然共用一份状态
（这也是它不能作为第一个试点的原因）。**第一个试点建议选"本来就多场地"的 TntRun**
（它的场地/会话已经按场地名分桶，把键换成房间 id 最自然）。

## 5. 已知的坑

- **`stampRoomLater`**：`/hub join` 之后框架会在 1/5/20 tick 重试把房间 id 盖到会话上
  （因为游戏的 `join` 可能延迟建会话）。改键之后这条仍然需要，别删。
- **房间销毁**：`GameSession.end()` 靠会话上的 `roomId` 决定删哪个房间。
  如果会话键换成了房间 id，注意**别把 `arenaName` 也写成房间 id** —— 那会让
  `maps.yml`/场地配置找不到场地（真实事故的形态：`arena().isReady()` 恒 false）。
- **`RoomManager.activeFor(gameKey)`**：多房间时返回 null 是**设计如此**（它只用于"恰好一个房间"的老路径），
  迁移后应该越来越少用到；发现某游戏还在靠它 → 那个游戏没迁干净。
