# 房间流程（当前 = 对齐上游的 features）

> 来源：用户 2026-11-01 转述的上游行为：
> 1. 加入房间等待，直到人数 **> 1**（即 ≥ 2）；
> 2. 人数 > 1 后 **30 秒**倒计时，然后开局（没有 OP 时）；
> 3. 队列里有 **OP** 时，开始权限交给 OP —— **无论人数够不够**，都等 OP 手动开。
>
> 用户明确说：**对这套流程不满意**，但要先与上游协商后再改。所以本版**按上游走**。

---

## 1. 好消息：这套流程在框架层**已经是统一的**

它就在 `MiniGameLib/com/hub/util/WaitCountdown` 里，而且 **24 个游戏全部都在用它**
（`grep -rln 'new WaitCountdown' 服务器小游戏插件/` → 24 个模块）。
类注释本身就写着"四个小游戏原来各抄一份 updateWaitCountdown/startWait/cancelWait"——**早年已经收敛过一次**。

所以"流程标准化"这件事，**等待阶段已经完成**，不需要新建机制。

## 2. 规则（就是代码里的四条，别记错）

| 条件 | 行为 |
| --- | --- |
| 队列里有 **OP** | **暂停**自动倒计时，等 OP 手动开始（提示"OP 在队列中，等待手动开始。"）|
| 人数 < `minPlayers()` | **取消**倒计时 |
| 人数 ≥ `maxPlayers()` | **3 秒**后开始（已跑的 30 秒会缩短为 3 秒）|
| `minPlayers ≤ 人数 < maxPlayers` | **30 秒**倒计时；加人/退人**不重置**正在跑的倒计时 |

参数位置（`WaitCountdown` 里的常量）：

```java
public static final int WAIT_SECONDS = 30;   // 达标但未满
public static final int FULL_SECONDS = 3;    // 满了
```

每个游戏通过 `WaitCountdown.Host` 提供 `minPlayers() / maxPlayers() / hasOpQueued()`。
**`minPlayers` 默认是 2**（多数游戏 `Math.max(2, cfgInt("min-players", 2))`），对应上游的"人数 > 1"。

## 3. 与"房间"的关系（D19/R3 之后要注意的点）

现在 `WaitCountdown` 是**按场地名**（`String` 键）分实例的，因为当时一个游戏只有一个场地。
房间化之后，同一个游戏会**同时存在多个房间**，每个房间都该有自己的一条等待队列与倒计时。

所以将来接房间时：

- `WaitCountdown` 的键要从"场地名"换成 **房间 id**（或 `gameKey + roomId`）；
- `hasOpQueued()` 要按**该房间内**的玩家判断，不能看全服。

**这一条现在不用改**（房间还没真正跑游戏），但改房间绑定会话（R5 `PARTY_MULTI` / 房间内开局）时必须一起改，
否则两个房间的倒计时会互相取消。

## 4. 如果之后要改这套流程（用户与上游协商后）

改动点集中、代价很小，因为只有一个实现：

| 想改什么 | 改哪 |
| --- | --- |
| 30 秒太长/太短 | `WaitCountdown.WAIT_SECONDS`（或改成可配置）|
| 满人 3 秒 | `WaitCountdown.FULL_SECONDS` |
| "有 OP 就暂停"这条要不要保留 | `WaitCountdown` 里 `hasOpQueued()` 的分支 |
| 人数门槛 2 | 各游戏 `Host.minPlayers()`（多数游戏已经有 `min-players` 配置项）|

> 用户对"有 OP 就完全暂停"这一点尤其可能想改（这条会让"OP 在旁边看"也变成"永远不开始"）。
> 但**当前按上游走，不动**。

## 5. 目标流程（用户拟定，**待与上游协商后实施**）

> 用户 2026-11-01 原话整理。**当前代码不是这样**，本版仍按上游流程（§2）。

### 5.1 规则

| # | 规则 | 与上游的差异 |
| --- | --- | --- |
| 1 | 倒计时 **30s → 300s**（5 分钟） | 更长，给"等朋友进房"留时间 |
| 2 | **本次对局最早加入房间的人 = 主持人** | 新增概念（上游没有主持人） |
| 3 | **开始游戏的权限在主持人手上** | 上游是"人够了就自动开" |
| 4 | **倒计时结束后游戏还没开始 → 把主持人踢出游戏** | 新增（上游没有这个惩罚） |
| 5 | **主持人主动退出游戏 → 重置倒计时** | 新增（换人当主持 / 重新等） |
| 6 | **OP 加入 → 主持权限交给 OP**，且**不再倒计时、也不限制最小人数** | 上游是"OP 在场就暂停倒计时"；这里更明确：**OP 可以一个人开** |

### 5.2 为什么这几条比上游好（我的看法）

- **主持人机制**解决"没人负责开始"的问题：上游靠"人够了自动开"，但**谁来等、谁该决定开不开**是模糊的。
- **规则 4（超时踢主持人）** 是这条设计里最关键的**反停滞**保险：如果没有它，
  "主持人挂机"会让房间永远卡在等待 —— 而这正是上游"有 OP 就永不开始"的同类问题。
- **规则 5（主持人退出→重置）** 让"换人"变成自然动作，而不是靠管理命令介入。
- **规则 6（OP 可单人开）** 保留了"管理员要测试/演示"的现实需求，且**不再需要**上游那种
  "OP 在就永久暂停"的粗暴做法。

### 5.3 落在代码上要改什么（将来实施时）

| 规则 | 改动点 |
| --- | --- |
| 300s | `WaitCountdown.WAIT_SECONDS`（建议顺便改成可配置） |
| 主持人 = 最早加入者 | 房间等待队列改成**有序**（现在多半是 Set），取头部；存入 session 的元数据 |
| 开始权限在主持人 | 开局的入口要校验"发送者 == 当前主持人"（OP 例外） |
| 超时踢主持人 | 倒计时归零但未开始时：把主持人移出队列（并给全房间提示），然后**重新计时** |
| 主持人退出 → 重置 | `leave()` 时若离开的是主持人，重置倒计时 |
| OP 加入 → 接管 | `hasOpQueued()` 的语义从"暂停"变成"**切换到 OP 主持模式**"：不自动倒计时、忽略 minPlayers |

⚠️ 规则 6 与上游的 `hasOpQueued()` 语义**不兼容**（一个是"暂停"、一个是"接管并放开人数下限"），
将来实施时是**替换**而不是叠加。

### 5.4 与房间化的耦合（重要）

这些规则都是**按房间**生效的（一个房间一个主持人、一条倒计时）。
所以实施顺序必须是：

1. 先把 `WaitCountdown` 的实例键从"场地名"改成"房间 id"（§3）；
2. 再加主持人 / 超时踢人 / OP 接管。

**顺序反了会出乱七八糟的串台**：两个房间共用一个主持人字段、或者 A 房的倒计时踢掉了 B 房的人。
