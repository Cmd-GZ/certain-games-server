# 坐标解耦清单（R2 施工表）

> 目标：让**游戏配置里不再依赖具体世界名**，这样房间（`room_xxx`，动态世界）才能跑起来。
> 验收基线见 `docs/框架不变量.md`；房间引擎见 `docs/房间引擎设计.md`。

---

## 1. 为什么必须解耦

现在所有场地坐标都长这样（HillKing 的真实配置）：

```yaml
arena:
  center: world_mini_game,627.50,53.00,307.50,178.8,85.0
```

房间化之后场地跑在 `room_hillking_1` 这样的**动态世界**里。如果配置跟着房间名走：

- 房间一删，配置就指向一个不存在的世界 → 场地"未配置"
- 每开一个房间就要改一次配置 → 完全不可用

---

## 2. 解决方案：世界 token（`com.hub.world.Worlds`）

坐标字符串的**第一段**叫「世界 token」，支持两种写法：

```
world_mini_game,627.50,53.00,307.50    ← 固定世界（旧配置，行为完全不变）
tpl:hillking_test,627.50,53.00,307.50  ← 模板作用域：解析成"该模板当前房间的世界"
```

框架提供三个方法（`MiniGameLib`，包 `com.hub.world`）：

| 方法 | 作用 |
| --- | --- |
| `Worlds.resolve(token)` | token → `World`；`tpl:` 走 `RoomManager.worldOfTemplate(key)`；解析不出来返回 `null` |
| `Worlds.tokenOf(world)` | 世界 → token；**如果这个世界是房间实例，返回 `tpl:<模板键>`**（不写临时房间名） |
| `Worlds.parse(raw)` / `Worlds.encode(loc)` | 上面两者的完整坐标版本，可直接替换各插件里的 `parse`/`encode` |

**安全设计**：没有存活房间时 `tpl:` 解析为 `null`，调用方必须按"场地未配置"处理
（不是崩掉，也不是退回别的世界）。

## 5. 注意（踩坑预告）

1. **`Worlds.tokenOf` 必须优先判房间**：否则在房间里 `/hill build` 会把 `room_hillking_1` 写进配置，
   房间一删配置就废（这正是"单一事实源"要防的那类 bug）。
2. **一个模板同时开多个房间时**，`worldOfTemplate` 返回"第一个"，只适合单房间阶段。
   多房间并行后，场地必须绑定到**具体 session**（R3 之后做），不能再靠模板查世界。
3. **模板世界的坐标是"模板内坐标"**：房间复制过去后坐标原样有效（同尺寸），但**区域声明**要跟着实例改名
   —— 房间引擎已经这么做了（`RoomManager.create` 里用 `roomId` 注册区域）。
4. 迁移期间**两种写法必须并存**，不能只支持一种——线上配置还没改。

## 6. ⚠️ MurderMystery 的 `tpl:` 路径还没跑通（附两个已修的数据丢失 bug）

实测把 4 个场地的 `world_key` 改成 `tpl:mm_test` 时，暴露了两个**会毁配置**的问题（都已修）：

### Bug 1：`save` 写 null 会把坐标擦掉（已修）

```java
if (loc == null) {
    sec.set(key, null);   // ← 场地没加载成功时 pos1 是 null → 直接擦掉磁盘上的坐标
}
```

改：**读不出来就跳过，绝不写 null**。原则是"'读不出来'必须表现为'不动它'"。

### Bug 2：`createSection` 会替换成空段（已修）

```java
ConfigurationSection sec = cfg.createSection("arenas");   // ← 整段变空！
for (arena : arenas) arena.save(sec.createSection(name)); // ← 每个场地也变空！
```

`MemorySection#createSection` 是"新建 + 覆盖"，不是"获取或创建"。改成先 `getConfigurationSection`，拿不到才 `createSection`。

**这一条和 R2「单一写者」是同一个病根**：不能用内存里的状态整份覆盖磁盘上不认识的内容。

### 还剩下什么（下一轮接着做）

1. **仍有第三条擦除路径**：上述两处修完后，场地段依然会变成 `{}`。
   现象：`mm reload` 之后场地仍未重读（`pos1` 仍是 null），关服时 `save()` 什么都不写，
   于是段是空的。**要先搞清 `mm reload` 是否真的重新 `Arena.load()`**。
2. **`join-signs` 没有走 token**：它们是 `List<Location>`，改 `tpl:` 会让 Bukkit 反序列化抛
   `Could not call method ... Location.deserialize`（刷 ERROR）。要么也做 token 化，要么明确"join-signs 只能在固定世界"。
3. **没找到其他 `(Location)` 直接 cast 的读取点** —— 但 ERROR 说明还有别的地方在反序列化这些 Location。

> **在 1、2 修好之前，不要在生产配置上把场地改成 `tpl:`** —— 有可能把坐标写丢。
> HillKing 那条链路是安全且已验证的，可以先照它的模式推广到结构化更简单的游戏。
