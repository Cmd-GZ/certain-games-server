# 坐标解耦清单（R2 施工表）

> 目标：让**游戏配置里不再依赖具体世界名**，这样房间（`room_xxx`，动态世界）才能跑起来。
> 验收基线见 `docs/框架不变量.md`；房间引擎见 `docs/房间引擎设计.md`。

---

## 1. 为什么必须解耦

现在所有场地坐标都长这样（HillKing 的真实配置）：

```yaml
arena:
  center: world_mini_game,627.50,53.00,307.50,178.8,85.0
```

房间化之后场地跑在 `room_hillking_1` 这样的**动态世界**里。如果配置跟着房间名走：

- 房间一删，配置就指向一个不存在的世界 → 场地"未配置"
- 每开一个房间就要改一次配置 → 完全不可用

---

## 2. 解决方案：世界 token（`com.hub.world.Worlds`）

坐标字符串的**第一段**叫「世界 token」，支持两种写法：

```
world_mini_game,627.50,53.00,307.50    ← 固定世界（旧配置，行为完全不变）
tpl:hillking_test,627.50,53.00,307.50  ← 模板作用域：解析成"该模板当前房间的世界"
```

框架提供三个方法（`MiniGameLib`，包 `com.hub.world`）：

| 方法 | 作用 |
| --- | --- |
| `Worlds.resolve(token)` | token → `World`；`tpl:` 走 `RoomManager.worldOfTemplate(key)`；解析不出来返回 `null` |
| `Worlds.tokenOf(world)` | 世界 → token；**如果这个世界是房间实例，返回 `tpl:<模板键>`**（不写临时房间名） |
| `Worlds.parse(raw)` / `Worlds.encode(loc)` | 上面两者的完整坐标版本，可直接替换各插件里的 `parse`/`encode` |

**安全设计**：没有存活房间时 `tpl:` 解析为 `null`，调用方必须按"场地未配置"处理
（不是崩掉，也不是退回别的世界）。

## 5. 注意（踩坑预告）

1. **`Worlds.tokenOf` 必须优先判房间**：否则在房间里 `/hill build` 会把 `room_hillking_1` 写进配置，
   房间一删配置就废（这正是"单一事实源"要防的那类 bug）。
2. **一个模板同时开多个房间时**，`worldOfTemplate` 返回"第一个"，只适合单房间阶段。
   多房间并行后，场地必须绑定到**具体 session**（R3 之后做），不能再靠模板查世界。
3. **模板世界的坐标是"模板内坐标"**：房间复制过去后坐标原样有效（同尺寸），但**区域声明**要跟着实例改名
   —— 房间引擎已经这么做了（`RoomManager.create` 里用 `roomId` 注册区域）。
4. 迁移期间**两种写法必须并存**，不能只支持一种——线上配置还没改。

## 6. ✅ MurderMystery 的 `tpl:` 路径已跑通（2026-11-01 收尾；含三个已修的数据丢失 bug）

> **⚠️ 本节的原判断（"只要 `readLoc` 绕开 `sec.get()` 就能用 `tpl:`"）已被实测推翻，以本节下半段为准。**
> 老写法（把 `world_key` 改成 `tpl:<模板键>`）**不是"读代码绕一下就好"，而是根本读不进来**。

### 6.1 根因：`tpl:` 不能写进 `==: org.bukkit.Location` 节点（错误发生在读代码之前）

把 `arenas.*.posN.world_key` 改成 `tpl:mm_test` 后，实测日志：

```
[ERROR]: [org.bukkit.configuration.serialization.ConfigurationSerialization]
         Could not call method 'public static org.bukkit.Location org.bukkit.Location.deserialize(java.util.Map)'
         of class org.bukkit.Location for deserialization
java.lang.IllegalArgumentException: unknown world
    at org.bukkit.Location.deserialize(Location.java:1229)
    at org.bukkit.configuration.serialization.ConfigurationSerialization.deserializeViaMethod(...)
    at org.bukkit.configuration.file.YamlConstructor$ConstructCustomObject.construct(YamlConstructor.java:58)
    at org.bukkit.configuration.file.YamlConfiguration.loadFromString(YamlConfiguration.java:121)
    at org.bukkit.plugin.java.JavaPlugin.reloadConfig(JavaPlugin.java:172)
    at org.bukkit.plugin.java.JavaPlugin.getConfig(JavaPlugin.java:149)
    at com.hub.util.StartCountdown.ensureDefaults(StartCountdown.java:111)
```

因果链（每一步都实测/字节码确认过）：

1. `==: org.bukkit.Location` 这个节点是 **SnakeYAML 在解析 YAML 时就**还原成 `Location` 的
   （`YamlConstructor.ConstructCustomObject` → `ConfigurationSerialization.deserialize` →
   `Location.deserialize`，里面直接 `Bukkit.getWorld(world_key)`）。
2. `world_key: tpl:mm_test` 不是已加载的世界名 → 每个坐标一行 `IllegalArgumentException: unknown world`
   （**不是返回 null，而是抛异常后被序列化框架兜住**）→ 该节点的值变成 `null`。
3. `YamlConfiguration.convertMapsToSections` 用 `section.set(key, null)`，而 Bukkit 的 `set(path, null)`
   语义是**删除键** → 内存里 `arenas.圣诞工厂` 变成空段。
4. 关服 `saveAll()` 按"读不出来就不动它"跳过写入 → `saveConfig()` 把空段原样写出 →
   `圣诞工厂: {}`，`world_key` 计数归零。

**所以"world_key 变 0"不是保存逻辑跳过，而是配置压根没解析出来、又被空段覆盖写出。**
也正因为错误发生在解析阶段，在 `readLocation/readLoc` 里怎么绕都没用（`sec.get()` 拿到的已经是 null）。

### 6.2 第二个坑：`sec.set(key + ".world_key", token)` 会毁掉坐标

想"保留原结构、只换 world 字段"也不行。`MemorySection#get/set` 的路径遍历都靠
`getConfigurationSection(key)`，而坐标的值是 `Location` 对象（不是 section）→ 返回 null →
`set` 走 `createSection(key)`，把整个 `Location` **替换成**一个只有 `world_key` 的空段。
（用 `javap -p -c` 读的字节码，不是凭印象。）

### 6.3 修法：房间世界用**字符串 token**，固定世界保持原生 Location

| 形态 | 磁盘长相 | 用在哪 |
| --- | --- | --- |
| 旧（不变） | `pos1: {==: org.bukkit.Location, world_key: minecraft:world_mm, x/y/z/pitch/yaw}` | **只用于固定世界** |
| 新 | `pos1: 'tpl:mm_test,-80.73,151.00,-59.72,-42.3,30.1'` | 房间实例世界（模板作用域） |

- `MiniGameLib / com.hub.world.Worlds`（1.7.3）：
  - `readLocation`：先看 `sec.isString(key)` → `Worlds.parse()`（`tpl:` 与固定世界名都认）；
    否则按旧格式读（`sec.get(key)` 拿 `Location`）。序列化 Location 里的 `tpl:` 分支保留，
    但只可能来自内存构造 —— 磁盘上这种文件根本解析不出来。
  - `writeLocation`：世界是房间实例 → 写 `Worlds.encode(loc)` 字符串；固定世界 → 照旧写原生 `Location`。
    **不再**改写序列化 Location 的 `world_key`/`world` 字段（见 6.2）。
  - 这条对另外 5 个用 `Worlds.writeLocation` 的游戏同时生效
    （BuildRun / ColorParty / DigToBottom / FootballArena / TntRun）—— 它们一旦进房间世界，老写法同样会毁配置。
- `MurderMystery`（1.1.1）：
  - `MurderMysteryArena.readLoc/writeLoc` 直接委托 `Worlds`（删掉重复实现）。
  - `MurderMysteryManager.load()` 末尾补 `publishRegions()`：`tpl:` 场地的世界是**运行时**才解析出来的，
    `/mm reload` 不重发一遍就永远补不上（`Regions.begin()` 先撤销本游戏旧声明，不会累积幽灵区域）。
  - `saveAll()` 的 `join-signs`：`createSection` → `Worlds.getOrCreate`。

### 6.4 存量场地怎么迁到 `tpl:`

**不要手改 `world_key`**（改完整份配置直接读不出来）。两种办法：

1. 在房间世界里用 `/mm setpos` 之类的命令重设一遍 —— 保存时会自动写成字符串 token；
2. 手工把那一行改成 `'tpl:<模板键>,x,y,z,yaw,pitch'`（x/y/z/yaw/pitch 照抄原来的五个字段）。

### 6.5 另两个已修的老 bug（仍然有效，别回退）

- **Bug 1：`save` 写 null 会把坐标擦掉** —— `if (loc == null) sec.set(key, null)` 必须禁止；
  "读不出来"要表现为"不动它"。
- **Bug 2：`createSection` 是"新建+覆盖"** —— 保存场地时用 `Worlds.getOrCreate(parent, path)`，
  不要 `createSection`。这条和 R2 单一写者是同一个病根。

### 6.6 ✅ 结案（2026-11-01）：第三种形态「裸世界名字段」，写入侧也要换 token

§6.3 那条修法只覆盖**存 `Location` 对象**的配置（MurderMystery 等 6 个游戏）。
还有第三种形态：**裸世界名字段**（HillKing 的 `center: <世界名>,x,y,z`、
HoldTheFort 地图文件的 `world: <世界名>`）。两半缺一不可：

| 半边 | 正确写法 | 写错的后果 |
| --- | --- | --- |
| 写入侧 | `Worlds.tokenOf(world)`（房间实例世界 → `tpl:<模板键>`，固定世界 → 世界名） | 在房间里做场地会把 `room_xxx` 写进配置，房间一删就失效 |
| 运行期比对 | `Worlds.tokenOf(实际世界).equals(配置里的声明值)` | 拿 `world.getName()`（`room_xxx`）和 `tpl:<键>` 比**永远不相等**，禁区/归属判断静默失效 |

HoldTheFort **0.2.0** 是按这条做完的第一例（读取侧 + 写入侧 + 5 处运行期比对），
语义与验证见 `paper-hold-the-fort/AGENTS.md`「重构状态」与 `改动记录.md`。

⚠️ 一个字段**同时**用于"落盘"和"运行期比对"时，两处必须用同一个 token ——
HTF 上一轮就是因为 `SetupSession#worldName` 一值两用，只能先做读取侧。

## 7. 顺带发现：`reload` 时旧区域没被撤销

JumpFill 的 `tpl:` 实测里，reload 前 24 块、reload 后 **25** 块（游戏数不变）——
说明重新声明时**新增了一块**，而不是替换掉旧的那块。

原因是 `RegionRegistry` 按 `(gameKey, arenaName, world)` 记账，世界名变了就被当成新条目。
**清理旧条目是 R2 的最后一块拼图**：让每个游戏在重新声明前先
`RegionRegistry.unregisterGame(gameKey)`（或按 gameKey 全撤再全注册）。

影响：不致命（重启即恢复），但会让 `[区域]` 统计越用越多，干扰 I2 的冲突判断。

## 9. ✅ MurderMystery `tpl:` 已通过（2026-11-01 收尾）

**结论**：上一轮的假设「`mm reload` 没重新调用 `MurderMysteryArena.load()`」**不成立** ——
`MurderMysteryCommand` 的 `case "reload"` → `manager.reloadConfigAndRescanGold()` → `load()`
确实重读了场地。真根因是 §6.1：`tpl:` 塞进 `==: org.bukkit.Location` 会让 YAML **解析阶段**
抛 `unknown world`、节点被删、关服写出空段。

另外确实还差一环：`load()` 重读场地后**没有重新声明地盘**（`publishRegions()` 只在 `onEnable`/`saveAll` 里调），
所以就算读对了，`/hub doctor` 的 `[区域]` 也不会变。这一环本轮一并修了。

**实测**（MiniGameLib **1.7.3** / MurderMystery **1.1.1**，29 jar / 31 插件，`tools/smoke.sh --deploy`）：

| 场景 | 区域 | ERROR |
| --- | --- | --- |
| 基线（`world_key: minecraft:world_mm`，pristine 配置） | 24 块 / 19 游戏 | 0 |
| `tpl:mm_test`、还没有房间（启动 + 关服，跑完一轮） | 20 块 / 18 游戏 | 0 |
| 同一进程：`hub room create mm_test mmroom` + `mm reload` 之后 | **24 块 / 19 游戏**（MM 的 4 块回来了，绑在 `room_mmroom`） | 0 |
| 关服后 MM `config.yml` | 16 处 `tpl:mm_test` 原样保留，`room_mmroom` 出现 **0** 次 | — |

> 数字口径：`tpl:` 场景的总数是 20（其余 18 个游戏）+ 4（MM 四块场地）= **24 块**。
> 24 → 28 那个预期是算错的口径（MM 的四块区域是它自己按场地坐标声明的，不是模板声明的；
> tpl 解析成功只是把这 4 块从 `world_mm` 平移到 `room_mmroom`，总数不变）。
> 若要 28，得在 `templates.yml` 里给模板另声明 `regions`（房间自己认领地盘），那是另一件事，本轮没做。

**迁移注意**（对剩下 7 个游戏同样适用，见 §6.3/§6.4）：

- 原生 `Location` 形态**只适用于固定世界**；
- 要让场地跟着房间走（`tpl:`），磁盘上必须换成字符串 token `'tpl:<模板键>,x,y,z,yaw,pitch'`；
- 别再用"把 `world_key` 改成 `tpl:xxx`"的办法，那会让整份配置在解析阶段就坏掉。
