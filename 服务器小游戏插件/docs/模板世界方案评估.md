# 「模板世界 / 游玩世界」方案评估

> 评估对象：上游提出的世界架构改造（0 模板/游玩二分、1 主城也从模板复制、2 房间化管理、3 单局小游戏＝无领奖台的派对）。
> 方法：把每个关键未知**实测**一遍，而不是估算。所有数字来自本机（btrfs / NVMe / Paper 26.2-126）。

---

## 结论先说

| 你的判断 | 评估 |
| --- | --- |
| 方向正确（模板 → 实例） | ✅ **强烈同意**。这是解决 `world_mini_game` 13 个租户互相踩的**根本办法** |
| 最大瓶颈是创建新世界的 IO | ❌ **不是**。实测复制 16MB 世界 **50–115 ms**，加载 15 个世界在同一秒内完成 |
| 主城也从模板复制 | ⚠️ **建议只对游戏房间做，主城保持持久世界**（理由见 §4） |
| 单局 = 无领奖台的派对 | ✅ 方向对，但要统一的是**协议**不是**流程**（见 §5） |

**真正的大头不是 IO，是「所有游戏的坐标与世界名解耦」——那是 19 个游戏的配置+代码迁移，工作量比 IO 大一个数量级。**

---

## 1. 实测数据（这是本文最重要的部分）

### 1.1 复制世界有多贵

| 操作 | 耗时 | 磁盘占用 |
| --- | --- | --- |
| 真实物理复制 16MB（`cp --reflink=never`） | **50 ms** | 16 MB 独占 |
| 真实物理复制 152MB（3 个世界） | **335 ms** | 152 MB 独占 |
| reflink 复制 152MB（`cp --reflink=always`） | **67 ms** | **0 B 独占** |

本机文件系统是 **btrfs**，原生支持 reflink（写时复制）。注意两点：

1. **`cp` 在 btrfs 上默认就自动 reflink**（`--reflink=auto`）——我第一次测"普通复制"时它其实也是 reflink，
   用 `btrfs filesystem du` 才看出来（`Exclusive 0.00B / Set shared 143MiB`）。
2. **Java 的 `Files.copy` 是逐字节复制，不会触发 reflink。** 想拿到 0 拷贝 + 0 磁盘，
   只能走外部命令 `cp --reflink=always`，或者用 JNI 调 `ioctl(FICLONE)`。这是实现约束，不是性能问题。

### 1.1b 生产环境是 **ext4** —— 没有 reflink，但依然不是瓶颈

上游确认面板跑在 ext4 上。这意味着 §1.1 里 reflink 那两行**在生产环境用不上**，一切按"真实物理复制"算：

| 操作（ext4 语义） | 实测耗时 | 说明 |
| --- | --- | --- |
| 复制 16MB 世界（不带 sync） | **50 ms** | 玩家点"创建房间"时无感 |
| 复制 16MB 世界（`sync` 落盘） | **115 ms** | 最坏情况，仍在一个可接受量级 |
| 删除 2 × 16MB 世界 | **59 ms** | 回收开销同样可忽略 |

所以结论不变：**IO 不是瓶颈，磁盘配额才是真成本**。两条实现约束：

1. **绝对不要写 `cp --reflink=always`** —— ext4 上会直接失败。用 `--reflink=auto`（自动回落到真实复制）
   或不带参数，这样在 btrfs 的开发机上还能白拿 0 拷贝。
2. **Java 的 `Files.copy` 在 ext4 上就是最普通的分块复制**，没有优化空间；这个量级（50ms/16MB）够用。

**模板瘦身能直接砍掉一半以上的磁盘与复制时间**：`world_gtb` 有 8 个 region 文件共 16MB，
但一块场地通常只落在 **1–2 个 region**（region 是 512×512 格的复制最小粒度）里。
把模板裁到必需区块后，单房间模板从 16MB 降到 **约 3–8MB**。

| 世界 | region 文件数 | 体积 | 瘦身后估计 |
| --- | --- | --- | --- |
| `world_gtb` | 8 | 16 MB | 3–8 MB |
| `world_duel` | 6 | 16 MB | 3–6 MB |
| `world_tr` | 4 | 11 MB | 2–4 MB |
| `world_mini_game` | **25** | **54 MB** | 拆分后每个游戏只需自己那 1–2 个 |

按"全服 10 个房间"算：不瘦身 ~160MB，瘦身后 ~50MB。**这两种都不算问题**，
真正要防的是「回收失败导致泄漏」，而不是单房间体积。

**一个 ext4 上特别划算的选项：把房间世界放 `tmpfs`（内存盘）。**

房间本来就是一次性的，放内存盘后：复制=内存速度、删除=瞬删、**重启自动清空（结构上不可能泄漏）**。
代价是 RAM：10 房间 × 8MB ≈ 80MB（本机 15GB 内存、服务端堆 2GB，完全够）。
风险是崩溃时房间数据丢失 —— 但房间本来就该丢，玩家回大厅即可。
对"回收逻辑写不对 → 磁盘慢慢满"这种长期运维风险，tmpfs 是釜底抽薪。

### 1.2 各世界的体积（未来的"模板"大小）

| 世界 | 大小 | 用途 |
| --- | --- | --- |
| `world_mm` | 64 MB | 密室杀手 4 个场地 |
| `world_mini_game` | 54 MB | **13 个游戏共用**的大杂烩 |
| `overworld` | 34 MB | 主城 |
| `world_gtb` / `world_duel` / `world_tnt` / `world_lp` | 15–16 MB | 各游戏场地 |
| `world_hp` / `world_htf` | 13 MB | |
| `world_tr` / `0Void World` | 11 MB | |
| `world_fb` / `world_wf` | 9 MB | |

**磁盘才是真成本**（不是时间）：不用 reflink 时，每个房间 = 模板大小。
5 个房间 × 16MB = 80MB 无所谓；但如果房间是 `world_mm`（64MB）级别、上限 10 个，就是 640MB。

### 1.3 运行时能不能建世界

✅ **能。** 实测 `/gw create testroom`：

```
[21:00:28] Selecting spawn point for level 'minecraft:testroom'...
[21:00:28] Loading 0 persistent chunks for level 'minecraft:testroom'...
[21:00:28] [GameWorlds] 世界 testroom 就绪：pvp=false 难度=NORMAL 怪物=false
[21:00:28] 已创建超平坦世界 testroom（固定白天，禁刷怪）。
```

关服时正常卸载存盘。**建立/加载世界不需要重启。**

### 1.4 「复制模板 → 当新房间加载」能不能走通

⚠️ **第一次失败了**，而且失败信息很有价值：

```
World minecraft:tmpl_test is a duplicate of another world and has been prevented from loading.
Please remove or change the duplicated Paper world metadata before loading it again.
```

原因：世界目录里带着**世界身份**，复制会把身份一起复制，Paper 认为这是重复世界。

✅ **删掉三个文件后就成功了**：

```
rm -f <房间目录>/data/paper/metadata.dat
rm -f <房间目录>/session.lock
rm -f <房间目录>/level.dat_old
```

结果：

```
[21:02:41] Loading 0 persistent chunks for level 'minecraft:tmpl_test'...
[21:02:41] [GameWorlds] 世界 tmpl_test 就绪：pvp=false 难度=NORMAL 怪物=false
```

**地形完整保留**（没有出现 `Selecting spawn point`，说明它加载的是我们的模板而不是重新生成）。

所以「模板 → 房间」这条链路**技术上完全可行**，实现时必须记得重生成世界身份。

## 2. 真正的瓶颈排序（按严重程度）

### ① 坐标与世界名解耦（**最大工作量**，不是 IO）

现在所有游戏的场地坐标都是这么存的：

```yaml
center: world_mini_game,627.50,53.00,307.50,...
pos1:  world_gtb,-23.0,127.0,-130.0
# 或者
world_key: minecraft:world_duel
x: 0.0  y: -1.0  z: 0.0
```

**世界名是写死在配置里的。** 房间世界的名字是动态的（`room_hillking_7f3a`），所以：

- 每个游戏的配置都要改成**模板相对坐标**（不带世界名，或只带模板名）；
- 加载房间时，由框架把"模板名"映射成"实例名"；
- 涉及 19 个已接入区域的游戏 + 各自 README / 建场命令的提示文案。

这是这次改造的**主体工作**，和 IO 无关。

### ② 磁盘配额与清理（会咬人）→ **ext4 上这是第一位的运维风险**

没有 reflink，磁盘按「房间数 × 模板大小」真实增长，所以回收逻辑必须可靠：
空置回收、上限、以及 `doctor` 里能看到"房间数 / 占用 / 最老空置"。

- 房间用完必须删；删漏了就是磁盘泄漏，而面板磁盘通常不大。
- 需要一个 reaper：空置 N 秒 → 先确认没有玩家/实体 → `Bukkit.unloadWorld(w, false)` → 删目录 → 从 `RegionRegistry` 撤销。
- 每个游戏要有房间上限（你说的第 2 点）。
- 建议：`/hub doctor` 显示「房间数 / 占用磁盘 / 最老的空置房间」，让泄漏看得见。

### ③ 主线程停顿（可接受，但要排队）

- 复制可以异步（50ms 无所谓）。
- **`Bukkit.createWorld` 必须在主线程**，这是硬约束。
- 单个房间 ≈ 0.1 秒，玩家点"创建房间"时无感。
- 但**派对一次要开 5 个房间**就是 ~0.5 秒 = 10 tick 卡顿。需要把房间创建排成队列、每 tick 只建一个。

### ④ 世界身份（已验证有解）

见 §1.4。不是难点，但**不做就一定失败**，而且错误信息（duplicate world）和真实原因（复制了身份）对不上，很容易查很久。

### ⑤ 模板编辑期的一致性

设计者在编辑模板时，如果有房间正在被创建 → 可能复制到"写了一半"的模板。
建议：**模板发布机制** —— 设计者改完执行 `/template commit`，框架把模板 reflink 成一份不可变快照，
房间一律从快照建。这样编辑和游玩彻底隔离。

### ⑥ 区域声明要跟着改（与已做的 I2 交互）

`ArenaRegion` 现在存**世界名**。房间化之后应该是：

```
模板声明一次区域 → 每个房间实例继承（只替换世界名）
```

这其实是好事（声明只写一遍），但意味着刚做的 19 个游戏要再动一次。不过逻辑很浅：注册时把模板世界名换成实例名。

### ⑦ 观战 / 菜单要变成动态视图

现在 hub 菜单的"场地羊毛"来自静态 `arenaInfos`；房间化之后**房间列表是动态的**。
这正是 P1b 的 `GameCatalog` 要做的事，而且和现有 `RegionRegistry`（运行时可注册）兼容。

## 3. 收益（为什么值得做）

1. **一次性消灭 `world_mini_game` 那 13 个租户互相踩的问题** —— 这是当前最脏的一类 bug 的来源
   （玩 A 游戏影响 B 游戏、gamerule 互相覆盖、区块/实体扫描串味）。
2. **场地管理从"手写坐标"变成"选地图"** —— 对不懂代码的运维是质变。
3. **多房间并行** —— 20 人上限可以同时开好几局，而不是排队。
4. **I2（区域归属）从"人记"变成"结构上不可能重叠"** —— 每个房间独立世界，天然不重叠。
5. 和已落地的 `GameSession` / `RegionRegistry` / `Failures` / `doctor` 全部兼容，不需要推倒。

---

## 4. 关于"主城也从模板复制"：建议不做

| 理由 | 说明 |
| --- | --- |
| 主城是唯一"玩家会留下痕迹"的地方 | 大厅建筑、公告牌位置、装饰；每次重启消失会让人困惑 |
| 玩家数据不能跟着复制 | `world/players/` 是玩家存档，模板复制会把所有人的位置/数据回滚 |
| 收益低 | 主城不需要"多实例"，它是全局唯一的大厅 |
| 风险高 | 大厅坐标写死在各插件配置里（`/hub set`、各处 `lobby`），一旦换世界名全部失效 |

**建议：主城 = 唯一的"持久游玩世界"；其余游戏世界全部模板化。**
这样"模板/游玩"的二分依然成立，只是主城作为"永远在线的那个游玩世界"。

---

## 5. 关于"单局小游戏＝无领奖台的派对"

方向对（统一协议），但要小心别把**流程**也统一了：

| 应该统一（协议） | 不应该统一（流程） |
| --- | --- |
| 房间的创建/销毁/归属 | 单局游戏不需要"等待室世界" |
| `GameSession` 生命周期 + `end(reason)` | 单局游戏不需要"领奖台传送" |
| 区域声明、观战落点、成绩记录 | 单局游戏不需要"随机抽下一个游戏" |
| 房间列表 / 观战列表 的展示 | |

也就是说：**单局 = `GameSession` 直接挂在房间世界上；派对 = 一个 `COMPOSITE` session 串多个子 session。**
两者共享同一套协议，但派对多一层编排。这与 `docs/会话模型草案.md` 里已经定下的 `COMPOSITE` 形状一致。

## 6. 建议的实施顺序

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **R1** | 房间引擎骨架：模板登记 / 房间创建（复制+删身份+加载）/ 销毁 / 空置回收 / 上限 | 用 `/room` 手工命令创建一个 HillKing 房间，进去能玩，走了自动回收 |
| **R2** | 坐标解耦：把 19 个游戏的场地改成模板相对坐标 | 每个游戏在房间里都能正常开局 |
| **R3** | 选地图 UI：玩家在菜单里选地图 → 创建房间 → 房间列表 | 你进游戏点两下就能开局 |
| **R4** | 清理/配额/监控进 `doctor` | `doctor` 显示房间数、磁盘、空置时长 |
| **R5** | 派对复用房间引擎（`COMPOSITE`） | 派对每局在独立房间里跑 |

**R1 可以先用 HillKing 一个游戏打通全链路**（它最小、已经接入区域声明），验证后再铺开。

## 7. 需要你确认的三件事

1. ~~生产面板的文件系统是什么？~~ **已确认：ext4。**
   → 不做 reflink 优化（写了反而会失败），按真实复制算；磁盘按「房间数 × 模板大小」增长。
   → 建议做**模板瘦身**（把每个模板裁到 1–2 个 region），并认真考虑**房间世界放 tmpfs**。

2. **能否接受"主城不做模板化"？**（我建议这样，理由见 §4）

3. **房间上限的期望值？** 比如"每个游戏最多 3 个房间、全服最多 10 个"——
   这决定了磁盘预算和清理策略。参考：全服 `max-players=20`。
