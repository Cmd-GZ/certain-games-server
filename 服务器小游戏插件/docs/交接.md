## 2. D22 是什么、怎么做（做同类改动照这个来）

### 问题

同一游戏开两个房间时，插件的 `Map<场地名, Session/Arena>` 与"一局的状态"都按**场地名**索引 →
两个房间共用一份状态、互相串台。

### 解法

**键从"场地名"换成"房间 id"**：`com.hub.room.RoomContext.roomKeyFor(player, gameKey, arenaName)`
（有房间用房间 id，没有就用场地名 —— 单房间行为完全不变）。
场地**坐标**仍按场地名查；两者语义不同，不要合并。

### 三种游戏形态（先判断，再动手）

| 形态 | 判断依据 | 做法 | 例子 |
| --- | --- | --- | --- |
| 甲 | 本局状态在 `XxxArena` 对象里 | 每房间 clone 一份 arena（`liveArenas`） | 谋杀密室、足球、建筑跑酷、决斗场、幸运之柱 |
| 乙 | 状态全在 manager 字段里 | **每房间一份 manager**（`XxxRooms` 路由） | OneShot、ArrowRain、FireJumper、SnakeParty、TNTBattle、GTB |
| 丙 | 有 `arenas` 表、状态也在 arena 里 | clone arena（**不要**再套 per-room manager，否则 N 个配置写者，违反 R2） | DigToBottom、TntRun、ColorParty |

### 四步法（每步都要编译 + 单房间回归）

1. 加辅助：`XxxArena.roomKey()` + `copyConfig()`；manager 加 `playerKey / keyArena / liveArenas` +
   `keyOf / arenaNameOfKey / liveArena / arenaByName`、`ensureSession(key)`。
   **这一步不改变任何行为**，回归结果必须和改之前一模一样。
2. `join` 用 `roomKeyFor(...)` 取键、本局状态落到本房间实例；`join()` **先挂会话再入队**（D23），返回 boolean。
3. 批量把"有玩家上下文"的 `arenas.get(...)` 换成 `liveArena(keyOf(player))`；
   无玩家的只读路径（收场/统计/刷告示牌）用 `arenaByName(...)`。
4. 运行时表（任务 / 计时 / 等待倒计时 / 尸体 / 计分 / 侧边栏键 / 区域声明名）的 key
   从 `a.getName()` 改成 **`a.roomKey()`**。

### 验证（缺一不可）


## 3. 十条踩过的坑（**每条都真炸过**）

1. **批量替换会误伤 `join()` 方法体**（踩了 4 次）：把 join 首行 `arenas.get(arenaName)` 换成
   `liveArena(keyOf(p))` → 那时键还不存在 → 恒 null → 表现为"场不存在"、命令返回 true、
   **控制台一行日志都没有**、会话不建。现在 `liveArena(null)` 会**直接抛异常**，但仍要排除 join 方法体。
2. **保存不能把运行时世界名写进配置**：房间销毁后 `save()` 会把 `room_xxx_1` 钉进磁盘 →
   下次开服该场地永远"未就绪"。已由 `Worlds.writeLocation/writeWorld` 兜住；新游戏**只写 `tpl:` 令牌**。
3. **多世界房间里 `room.world` 只是"第一个世界"**：派对房间 = 迷你小游戏世界 + 各游戏模板。
   钉世界要按 `room.arenasOf(gameKey)` 里**这张图**的 `ArenaSlot` 取；`tpl:` 也解析到 `room.world`，
   所以 `pin()` 不是可选项。
4. **控制台命令没有房间上下文**：派对开局是 `dispatchCommand(控制台, "<game> start")`。
   已在 ArcadeParty 委派处套 `withPartyRoom(...)`；**游戏自己的 `start` 处理器是否用它**还要各自确认。
5. **"每房间一份 manager"下别写"非默认实例 saveAll → defaultManager().saveAll()"漏斗** —— 会自我递归爆栈。
6. **批量替换要排除字符串字面量**：曾把 `{stars}` 换成 `{party.stars}`，直接改了玩家可见的计分板变量。
7. **登记成派对子游戏后 `/hub create <game>` 会被套壳成派对房间**（HubCore 的 `PartyGames.isSubGame`）：
   单房间回归会看到"会话=NO + ⚠ 进房后没有会话"。跑回归前先把 `games.<game>` 从**测试副本**配置里撤掉。
8. **派对的子游戏清单来自房间地图的 regions（`Room.subGames()`），不是 ArcadeParty 的 `games:` 段**：
   用独立模板的游戏必须给派对图加世界 + 区域，否则被"取交集"过滤掉、派对不开那一关。
9. **不要在子 agent 干活时自己跑冒烟**：两个 agent 共用 `.server/run_alt` 会 `session.lock` 锁死。
10. **房间/回归标签必须小写**（`regress-a.sh <list> LABEL`），大写会生成非法房间名。
11. **`/hub create` 的报错只发给玩家，不进控制台**：地图名写错时，日志里**一行都没有**（只有玩家聊天栏能看到），
    很容易误判成"代码坏了"。回归里 `建房=NO` 先怀疑**地图名**（`.server/list-full.txt` 里的是权威名单，
    例如 `luckypillar` 的地图是 **虚空**，不是显示名）。

   （anvilbattle 一房 6 秒分出胜负、另一房两人站着不动一直不结束），**不是串房**。
   下一步：挑固定时长的局，或让假玩家做"触发淘汰"的动作。2026-11-05 有进展：修掉"只有一间 RUNNING"之后，

```bash

                                 # 单局全流程：建房 → 进房 → **[RUNNING]** → 收场 → ERROR 0

                                 # 两房各跑一局：两房同时 RUNNING → 各自 ROUND_END → ERROR 0
```
