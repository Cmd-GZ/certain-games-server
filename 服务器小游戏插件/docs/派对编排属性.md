# 派对编排属性（PARTY_OF_ONE）设计稿 —— 第一期已落地

> 这一轮要回答的问题：**怎么把"单个小游戏"包装成"只有一个游戏、没有领奖流程"的派对，
> 而又不引入父子 session 的复杂度？**
>
> 结论（决策 **D17**）：**"派对"不是 session 类型，而是房间/对局的一种「编排属性」**。
> 单局游戏（`SINGLE`）与单局包装成派对（`PARTY_OF_ONE`）**共用同一条执行路径**：
> 一个房间、一个 session、一个 `end(reason)`；差别只在展示层（有没有领奖台、有没有"下一局"）。
>
> 判断只有一条：**父 session 是否必须比子 session 活得久。**
>
> | 形态 | 父比子活得久？ | 会话树 | 谁实现 |
> | --- | --- | --- | --- |
> | 单局游戏 `SINGLE` | — | 1 个 session（游戏自己的） | 各游戏（HillKing 已完成） |
> | **单局包装成派对 `PARTY_OF_ONE`** | ❌ 游戏结束 = 整局结束 | **1 个 session（派对自己的）** | **本轮：ArcadeParty `flow: single`** |
> | 多局派对 `PARTY_MULTI` | ✅ 第 1 局结束派对还得活着 | 父 + N 个子 | **第二期**（等被包装游戏自己接入 session） |

---

## 1. `flow` 声明在哪一层？—— 插件配置（`ArcadeParty/config.yml`）

```yaml
flow: party          # party = 多局串烧（现状）；single = 单局包装成派对（PARTY_OF_ONE）
flow-game: ''        # 本场只允许这几个小游戏（key，留空 = 不限制）；room 化之后来自房间模板
```

运行期：`/arcade flow <party|single> [小游戏key|-]`（OP），写回 `config.yml`（单一写者）。

**为什么不是直接写进 `MiniGameLib/templates.yml`（房间模板层）？**

D17 的措辞是"房间的编排属性"，最终形态确实应当跟着房间走。但**房间 ↔ 派对的绑定还没做**
（`docs/房间引擎设计.md` §8 把"派对复用房间"排在 R5）。现在把 `flow` 写进模板，
`RoomManager` 读出来之后**没有任何人会用它** —— 那是一个死键，比不放更糟。

所以第一期的做法是：**执行路径按最终形态实现，只把"数据来源"留在插件配置**。
等房间能绑定派对时，只改 `ArcadePartyManager#flow()/flowGame()` 的取值来源
（从绑定房间的模板读），流程代码一行不动。这是"先落地路径、后落地来源"。

## 2. `PARTY_OF_ONE` 怎么复用单局路径？

```
join（等待区，无 session）
  → startParty：
      selected = [1 个游戏]              ← 与 party 的唯一选择差异（effectiveGamesPerParty() == 1）
      session = new ArcadePartySession   ← 整场派对 = 1 个 session，children 恒为空
      session.join(每个参与者)            ← I1：玩家挂到归属链上
      session.start()                    ← WAITING → RUNNING（I5）
  → TRANSITION（准备）→ ROUND（派发该游戏的 join/start 命令）
  → finishRound：本局结束
      if flow == single → endParty(ROUND_END)   ← 整场结束，**不进领奖台、没有"下一局"**
      else             → 还有下一局就 beginTransition()，否则 beginPodium()
  → endParty/abortParty → session.end(reason) → onEnd → doEndParty（唯一收场，I4）
```

`beginPodium()` 里还有一道防御：`flow == single` 时直接收场（正常路径根本到不了它）。

**行为差异只有三处，全部在展示层**：

| 位置 | `flow: party` | `flow: single` |
| --- | --- | --- |
| 局数标签 | 「第 1/3 局」 | 「本局」 |
| 开局播报 | 「本局共 3 个小游戏：…」 | 「单局派对（PARTY_OF_ONE）：… 打完即结束，没有颁奖典礼」 |
| 收场 | 打完进颁奖台 → 揭晓 → 回大厅 | 这一局结束就收场，直接回大厅 |

玩法、计时、星星、计分板、场地/命令派发**完全同一条代码**。

## 3. 领奖台 / "下一局" 怎么被关掉？

不是"新加一个模式分支"，而是**在原有分岔点上加一个出口判断**（`finishRound` 末尾）：

```java
roundIndex++;
if (isPartyOfOne()) { endParty(EndReason.ROUND_END, "&6&l派对结束！"); return; }  // ← PARTY_OF_ONE
if (roundIndex >= selected.size()) beginPodium(); else beginTransition();
```

`beginPodium()` 开头同样有一道 `isPartyOfOne()` 防御。收场统一走 `GameSession.end(reason)`，
`doEndParty()` 里用 `podiumShown` 记录"本场到底有没有走过颁奖台"，冒烟台据此断言
（`[派对] 收场 reason=ROUND_END，flow=single，走过颁奖=0`）。

## 4. 与 `GameSession` 的关系：一个 session，不用 children

* `ArcadePartySession extends GameSession`，key = `arcade`，`arenaName` = `主场地`。
* **每次派对新建一个**，`end()` 后丢弃（不是插件启用时就建好 —— 那样第二次开局会撞 I5 的转移表，
  这一点 HillKing 现在就是这么踩的，见 `docs/改动记录.md` 最上面一条"遗留"）。
* `parent/children/adopt` **保留但单局路径不启用**：子树永远为空（D17 明确要求保留，第二期用）。
* 参与者经 `session.join(玩家)` 挂到归属链 → `/hub doctor` 的 `[归属]` 在派对期间不再是 0，
  这是 I1 第一次在"派对"这种形态上真正生效。

## 5. 第二期（`PARTY_MULTI`）留什么

| 事项 | 前置条件 | 归属 |
| --- | --- | --- |
| 每局一个小游戏 session，由派对 `adopt` 成子会话 | 被包装的小游戏自己接入 `GameSession`（现在只有 HillKing 1/24 接了，而且它不 attach 玩家） | 游戏迁移的收官轮 |
| 父 session 活过子 session（局间累计星星/淘汰） | 同上 | 同上 |
| `flow` 从房间模板读（一个房间跑哪场派对） | 房间 ↔ 派对绑定（`docs/房间引擎设计.md` R5） | 房间化那一轮 |
| 单局派对跑在房间世界里（`tpl:` 场地） | 被包装游戏的场地支持 `tpl:`（MurderMystery 已做，其余 6 个还在清单里） | 坐标解耦收尾 |

一句话：**第一期把"单局"这条最平的路修完并验证了；"多局"这条要等被包装的游戏自己先变成
session —— 顺序不能反，反了就是"父 session 管着一堆不存在的子 session"。**
