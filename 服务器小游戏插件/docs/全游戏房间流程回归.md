## 未通过的 11 个分成两组，原因不同

### A 组：非子游戏，进房后自身会话没建起来（6 个）

`buildrun`、`football`、`duel(重锤)`、`luckypillar`、`murdermystery`、`tntbattle(双岛)`

这些游戏的 join 命令形如 `<game> join {arena}`，进房后执行了但没建会话。
共性是**场地就绪判定**：它们的 arena 在启用时解析 `tpl:` 失败，
框架的"进房前重载"已执行，但游戏自身的 `join()` 仍认为场地未配置
（对照：`gtb` 同类但**通过**，说明不是框架层问题，而是各游戏 `join` 里的就绪判定/坐标解析差异）。

### B 组：子小游戏，派对没开局（5 个）

`colorparty`、`digdown`、`grouprace`、`jumpfill`、`landclaim`

其中 **`digdown` 已确认是 key 不一致**：`maps.yml`/`games.yml` 用 `digdown`，
而 ArcadeParty 的 `games:` 列表用 `digtobottom` → `PartyGames.isSubGame("digdown")` 为 false →
**没有被套壳成派对**，于是按普通游戏走 `<game> join`，又落到 A 组那类失败。
其余 4 个需要逐个看是"没被委派"还是"委派了但游戏没接住"。

## 这一轮顺带修掉的三个真 bug

1. **`startParty` 读字段 `lobby` 而不是 `getLobby()`** → 倒计时到点静默 return；
2. **框架"进房前重载"每个玩家都触发一次** → 第二次重载调用游戏 `load()`，
   而 `load()` 会 `waiting.clear()`，**把前一个玩家从派对队列里挤掉**（`waiting` 永远是 1，
   永远不满足 `min-players=2`）。已改为**每个房间只重载一次**；
3. 回归夹具：`long90.txt`（90 行 doctor）会让服务器在派对开局前关服 → 改用 `long200.txt`。
