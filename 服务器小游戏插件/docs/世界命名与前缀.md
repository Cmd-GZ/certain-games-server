# 世界命名与前缀规则（计划，未实现）

> 来源：用户 2026-11-01 的要求 —— 模板世界与游玩世界各用各自的前缀；
> `/gw` 创建世界时若名字没带前缀则**默认补模板前缀**以防冲突，除非管理员显式强制。
> 状态：**计划**。实现时机见 §5（我决定：与 R3 选房 UI 同批）。

---

## 1. 前缀家族（三段命名空间）

| 前缀 | 谁创建 | 用途 | 开服时是否加载 |
| --- | --- | --- | --- |
| **`tmpl_`** | 管理员 `/gw create`（默认）；或房间引擎的模板登记 | **模板世界**：设计者编辑的地图源，只被复制、**永不当场地加载** | ❌ **不自动加载**（需要时手动 `/gw load`） |
| **`room_`** | **只有房间引擎**（`RoomManager`） | 房间实例：从模板复制出来的动态世界，用完即删 | ❌ 引擎按需建/删 |
| **无前缀**（`world`、`hub`…） | 管理员 `/gw create --persist` | **持久世界**：主城这类"长期存在、玩家会留下痕迹"的世界 | ✅ 照旧自动加载 |

### 为什么持久世界**不**用 `room_` 前缀（用户给过两个方案，我选后者）

用户提过两种：① 把主城也当"特殊 room"，前缀用 `room_`；② 持久世界单独一类、不加前缀。

**选 ②**，理由是 `room_` 这个前缀的含义应该是"**引擎管生管死的一次性实例**"：

- 房间引擎会**自动回收** `room_` 世界（空置超时就删）。名字一旦带上 `room_`，
  就等于告诉所有代码和运维脚本"这东西可以被回收"。
- 主城恰恰相反：它是**唯一的、永久的、玩家在里面留痕**的世界（D1）。
  给它 `room_` 前缀，就是在命名层面暗示"它可以被删掉" —— 这是最危险的那种暗示。

所以命令的第二层语义是"**你要造的是哪种世界**"，而不是"要不要跳过前缀"：

```
/gw create <名字>            → 造模板（自动补 tmpl_，不自动加载）
/gw create --persist <名字>  → 造持久世界（不补前缀，开服自动加载）
```

**为什么必须分前缀**：房间化之后，"这块地是世界模板、还是一份临时实例、还是长期存在的主城"
是**三种完全不同的生命周期**。靠名字前缀区分比查配置表更可靠 ——
引擎、`doctor`、运维清理脚本都能一眼看出一个目录是干什么的。

## 2. `/gw create` 的四种世界（kind 词形式）

```
/gw create template          <名字> [void]   # 造模板：自动补 tmpl_，不自动加载
/gw create persist           <名字> [void]   # 造持久世界：拒绝 tmpl_/room_ 前缀，开服加载
/gw create room              <模板> [房间名]  # 从模板复制一份房间（名字可省，引擎生成 room_<短名>_<序号>）
/gw create no-preserve-world  <名字> [void]   # ⚠ 危险逃生舱：不做任何前缀/归属检查（需三次确认）
```

**为什么是 kind 词而不是 flag**：四种世界的性质不同，用词表达"你要造哪一种"比用 flag 表达
"要不要跳过某条规则"更清楚；而且全部用词，语法一致（不会出现"下一个参数是词还是 `--x`"的猜测）。

### 一致性检查（template / persist 两种）

| 命令 | 名字前缀 | 结果 |
| --- | --- | --- |
| `create template X` | 无前缀 | → **`tmpl_X`** |
| `create template X` | `tmpl_` | 模板 |
| `create template X` | `world_` | ❌ 拒绝（那是持久世界的名字） |
| `create template X` | `room_` | ❌ 拒绝（房间由 `create room` 造） |
| `create persist X` | 无前缀 / `world_` | 持久世界 |
| `create persist X` | `tmpl_` | ❌ 拒绝（语义矛盾） |
| `create persist X` | `room_` | ❌ 拒绝 |

### `create room`：为什么房间名不能从模板名 1:1 推出来

`tmpl_hillking_test` → `room_hillking_test` 这种纯替换**不够**：同一模板要能开多个房间（D2 上限 8），
第二个就撞名了。所以房间名由引擎生成 **`room_<模板短名>_<序号>`**，也可以手给一个后缀。

### `no-preserve-world`：三次确认的危险门

它等价于 `rm --no-preserve-root` 的思路——**跳过全部保护**，可能造出框架不认识的世界
（例如名字像房间、却不在房间引擎登记里的"僵尸世界"，回收/区域/会话都不会认它）。

所以它要求**连发三次同一条命令**（每次打印 `确认进度 n/3`，2 分钟内有效）：
- 普通 `delete` 本来就是"命令 + `confirm`"两次；
- 危险形态再高一级 → **三次**。

## 2.5 `/gw delete` 同样按 kind 分派

```
/gw delete template|persist|room|no-preserve-world <名字> [confirm]
```

- **kind 是安全断言**：你声明它属于哪一类，名字对不上就拒绝（`类目不匹配：p1 实际是 persist，你声明的是 template`）。
- `room` 的删除**交给 `RoomManager.delete`**：先踢人 → unload → 删目录 → **撤销区域注册**。
- `no-preserve-world` 同样是三次确认。

## 3. 配套：`tmpl_` 世界不自动加载

这是**必须一起做**的一条，否则规则自相矛盾：默认补 `tmpl_`，而 GameWorlds 又会把
配置里登记的世界全部在开服时 `createWorld` —— 模板就被加载了（违背"模板永不加载"）。

做法：`GameWorlds` 读到名字以 `tmpl_` 开头的条目时，登记为**托管但不自动加载**
（`load: false` 语义），需要时用 `/gw load <名字>` 手动加载（设计者建图时用），
`/gw unload` 收回。

## 5. 实现时机（我决定）

**与 R3（选房 UI）同一批做**，理由：

- R3 要让玩家"选地图 → 建房间"，**第一步就是列出可用模板** → 必须有可靠的"哪些目录是模板"的判定，
  而前缀是最便宜的判定方式（不用读模板登记表，也不依赖配置是否被手改）。
- `tmpl_` 不自动加载这条，直接影响"开服时到底加载了几个世界"（也直接影响那 3.6s 的启动存盘开销）。
- 两件事都改 `GameWorlds` + `RoomManager`，合并做比分开做少一轮构建/冒烟。

**在此之前不改**：现在 `tmpl_` 世界在 `templates.yml` 里是手工登记的（`folder: tmpl_xxx`），
房间引擎只把它们当"复制源"，不加载，所以当前行为是正确的；缺的只是 `/gw create` 的便捷入口与强制力。

## 6. 历史世界的处置（用户 2026-11-01 明确）

> "历史世界由于需要为重构后的项目服务，所以都可以改成 `tmpl_`。"

也就是：现有的 `world_gtb` / `world_mm` / `world_duel` / `world_lp` / `world_tr` / `world_hp` /
`world_tnt` / `world_fb` / `world_wf` / `world_mini_game` / `0BB-Candyland` / `0MM-SantaFactory` 等
**全部视为未来的模板**，重命名成 `tmpl_<原名去掉 world_ 前缀>`。

### 这是一次真正的迁移（不是改个名字）

世界名 = Paper 里的目录名 = 所有配置里坐标的第一段。所以一次重命名要动四处：

1. `world/dimensions/minecraft/<旧名>/` → `<新名>/`
2. 各游戏配置里坐标的**世界第一段**（`world_mm,6.0,80.0,-34.0` → `tmpl_mm,6.0,80.0,-34.0`）
3. `GameWorlds/config.yml` 里登记的世界名
4. 区域表重新生成（`tools/region-report.py`）+ `/hub doctor` 复核

**工具能帮上忙的地方**：我们已经有了 `com.hub.world.Worlds` 的 token 机制。
迁移时可以先把配置改成 `tpl:<模板键>`（这样房间实例化后自动指向房间世界，永久脱离具体世界名），
**重命名反而变成次要问题**。

### 排序（我定的）

| 步骤 | 内容 | 依赖 |
| --- | --- | --- |
| **N1** | `/gw create` 前缀规则 + `tmpl_` 不自动加载（本文件 §2/§3） | 无 |
| **N2** | R3 选房 UI（先用现有唯一模板 `tmpl_hillking_test` 打通） | N1 |
| **N3** | 历史世界批量重命名 + 配置改 token | N2（要等 UI 能验证"模板列表正确"） |

**N3 必须放在 N2 之后**：重命名会同时改动 19 个游戏的配置，没有一个"能列出模板并验证"的入口，
改错了只能靠冒烟的数字猜 —— 而 R3 正好提供那个入口。

## 7. 模板世界与"地图"的关系（2026-11-02 更正）

之前这里含糊地说过"map ↔ 模板世界不是 1:1"，现在把实证写清楚：

**`world_mini_game` 就是"一个模板世界装多张地图"的现实例子。**
区域表里这些场地**都在同一个世界**里：

```
snakeparty      @world_mini_game
animalslaughter @world_mini_game
hillking        @world_mini_game
tntrun / ...
```

所以正确的模型是：

| 概念 | 含义 |
| --- | --- |
| **模板世界** | 一张"大地图集"（如 `world_mini_game`）|
| **地图 / 小游戏** | 模板世界里的**一块区域 + 一个场地名**（如"高地之王"那块高地，场名 `hillking`）|
| **房间** | 从模板世界复制出来的一份实例；一个房间**只服务一张地图** |

由此 `/hub create <游戏> <地图>` 的正确流程是：

```
<游戏> + <地图>  →  查出这块地图属于哪个模板世界 + 它的场地名
                 →  /gw create room <模板世界>
                 →  房间初始化时把"场地名"交给游戏（就是 join-command 里的 {arena}）
```

**当前实现的差距（如实标注）**：`templates.yml` 只登记了 `key` + `folder`，
**没有"地图清单"**，所以 `/hub create` 现在只能按模板键/目录名匹配。
要支持"一张模板世界多张地图"，模板登记需要多一层：

```yaml
templates:
  mini_game:
    game: arcade
    folder: tmpl_mini_game
    maps:                       # ← 新增：这个模板世界里有哪些地图
      hotpotato: { arena: 群系 }
      hillking:  { arena: hillking }
      tntrun:    { arena: TNTRUNround }
```

房间创建时按 `maps` 解析 `<地图>`，并把 `arena` 记进房间，供 `/hub join` 的 `{arena}` 使用。
**命令形式不用变**。
