# 玩家可见流程（读项目后整理，2026-11-02）

> 这份文档回答一个问题：**玩家在服务器里到底看到什么、按什么顺序做**。
> 重构时代价最大的一类错误，是"代码改对了、但玩家明显能看见的东西被漏掉"。
> 所有结论都是从 `.server/run/.../plugins/` 的真实配置 + HubCore 源码读出来的，不是推测。

---

## 1. 进服 → 主城

`HubListener#onJoin` → 延迟 1 tick → `HubManager#teleportToLobby(p)`：

| 动作 | 代码 |
| --- | --- |
| 清空**整个背包 + 四件甲** | `p.getInventory().clear()` / `setHelmet(null)…` |
| 给**指南针**：「&e小游戏菜单 &7(右键打开)」 | `giveMenuItem`，固定放第 **4** 格（被占时就近顺延）|
| 一律切**生存**模式 | 防止淘汰/观战遗留的创造或旁观在重连后"无敌/穿墙" |
| 满血、满饱食、清药水效果 | `setHealth(20)` / `setFoodLevel(20)` / 移除效果 |
| 传送主城出生点 | `lobby:` 配置（world/x/y/z/yaw/pitch）|

指南针用 **PDC 标记**（`gamehub:menu-item`）识别，不是靠材质 —— 因为杀手等游戏也会给玩家指南针（追踪用）。

## 2. 指南针 → 游戏菜单

右键指南针（`HubListener#onInteract`）→ `openMenu` → `MenuLayout` 渲染的箱子界面：

- 标题配置在 `menu-title: 游戏大厅`，行数 `menu.rows: 6`
- 每一格由 OP 用 `/hub menu edit` 摆（配置里是 `menu.items.<槽位>`）
- **玩家侧**：`SHIFT+左键` 可以"只看提示（lore）"，方便核对
- 材质识别同样用 PDC（`gamehub:menu-item`）；**没标记的同材质物品只在大厅里**才当菜单用，
  否则游戏内的指南针会误开主城菜单

菜单当前内容（2026-11-03，**由注册表派生**，见下）：

- **根菜单**（12 项）：建筑猜猜乐 / TNT 对战 / 街机派对 / 单挑 PvP / 密室杀手 / 绿茵足球 /
  你建我跑 / 幸运之柱 / TNT大战 / **迷你小游戏（子菜单，史莱姆球）** / **观战（末影之眼）** / 头衔菜单
- **「迷你小游戏」子菜单**（16 项，全是派对的子小游戏）：烫手山芋 / 雪塔大作战 / 色盲派对 /
  一掘到底 / 铁砧掘战 / 动物屠宰 / 蛇行派对 / 群友竞速赛 / 击退大战 / battlefield 1 (占地1) /
  跳水填格 / 记忆翻牌 / 高台之王 / One Shot / 跃火者 / 万箭齐发

### 菜单不再靠手配（R1：由注册表派生）

`MenuLayout.ensureDerivedGameEntries()` 在开服 40 tick 后跑一次：

- **子小游戏**（`PartyGames.all()`）→ 进「迷你小游戏」子菜单；
- **其余游戏**（含街机派对）→ 根菜单各一项；
- 入口动作统一是 `game:<显示名>`；
- **只补空槽、不改已有布局**；没空槽就报警让人 `/hub menu edit` 手动加；
- 顺手清掉**重复的旧 `cmd:<游戏> join`**（房间化后那些点不通）——只有当该游戏已有 `game:` 入口时才删，
  命令**别名**也认（`party` 是 `/arcade` 的别名）。

配套的启动审计（R3）会报出"已登记但菜单里点不到"的游戏。当前剩 3 个，都是**故意不补**的：
`天坑`（D26 公共设施型，不需要房间入口）、`粒子枪战` / `战线模式`（`maps.yml` 里没有地图）。

> `quark`（粒子枪战）与 `holdthefort`（战线模式）在 `games.yml` 里有命令但**没有地图**，
> 由 `[key审计]` 持续报出来，等你决定是补数据还是摘掉。

## 3. 菜单动作的五种类型（`MenuLayout#parseAction`）

| 动作 | 含义 | 例子 |
| --- | --- | --- |
| `cmd:<命令>` | 以玩家身份执行命令 | `cmd:gtb join` |
| `game:<游戏>` | 打开该游戏的**场地子菜单** | `game:单挑 PvP` |
| `open:<子菜单名>` | 打开自定义子菜单 | `open:迷你小游戏` |
| `arena:<游戏>\|<场地>` | 直接进某个场地 | `arena:密室杀手\|ship` |
| `spectate` | 打开**观战列表** | 末影之眼那一格 |

`op-only: true` 的格子只对管理员显示。

## 4. 点游戏 → 场地判断（`HubManager#clickGame`）

```
点游戏图标
 ├─ 场地数 == 1      → 直接执行该游戏的加入命令（bestJoinCommand → dispatchCommand）
 ├─ 场地数 > 1       → 打开场地子菜单（子菜单用**实时状态**渲染成羊毛，等待/进行中颜色不同）
 └─ 没有等待中的场地，但这一局在打 → **直接进观战**
```

> ⚠️ **重构注意**：`clickGame` 的"1 个场地"分支走的是 `dispatchCommand`，
> **不经过 `joinArena`**。R3 的房间化分流必须**同时**放在 `clickGame`（本层）和 `joinArena`，
> 只在 `joinArena` 里做的话，最常见的入口会失效。（2026-11-02 已修）

## 5. 加入一局（以高台之王为例，`HillKingManager#join`）

玩家看到 / 感受到的完整顺序：

1. 清游戏状态、切生存、`resetPlayer`
2. **传送到场地等待区**（`arena.getLobby()`）
3. 背包换成**等待室道具**：
   - 「&a&l返回大厅 &7(右键)」（红床，格子可配）
   - 如果是管理员，多一个**开局道具**（第 `start-slot` 格）
4. 公屏播报：`[游戏名] 玩家名 加入了游戏`（`HubAPI.announceJoin`）
5. **tab 列表**里名字变成 `&e[等待中·高台之王] 名字`
6. 聊天框提示：`已加入高台之王等待队列 (1/8)`、`人数达到 2 后自动倒计时开始。`
7. 等待期间 **actionbar** 显示倒计时（`&7等待中 | &f开始倒计时 &e30s`）

## 6. 等待 → 开局

`WaitCountdown`（D20/D21 说的那套）：

| 条件 | 行为 |
| --- | --- |
| 人数 < min（默认 2）| 取消倒计时 |
| min ≤ 人数 < max | **30 秒**倒计时 |
| 人数 ≥ max | **3 秒**倒计时 |
| 队列里有 OP | 暂停自动倒计时，等 OP 手动开 |

（D21 的目标流程：300s / 主持人 / 超时踢主持人 / OP 接管 —— **已获上游同意，未实施**）

## 7. 游戏内

- actionbar 显示剩余时间（各游戏自己的实现，如 HillKing `&6高台之王 | &f剩余 &eXs`）
- 淘汰/结束 → 结算 → 传送回主城（`HubAPI.teleportToLobby`）
- 游戏里还有一个「**回主城**」道具（`gamehub:hub-item` 标记）：**右键 = 退出所有游戏并回主城**，
  这个道具**在任何游戏里都能用**，是玩家最重要的逃生出口

## 8. 观战

| 步骤 | 细节 |
| --- | --- |
| 入口 | 菜单里**末影之眼**那一格（`spectate`），或在"没有等待场地但正在打"时点游戏图标 |
| 条件 | 必须在**大厅**（还在游戏里会提示先退出）|
| 落点 | 优先用游戏上报的观战点（`HubAPI.setArenaSpectator`），否则落到某位存活玩家头顶 3 格 |
| 状态 | 切 **SPECTATOR** 模式，**清空背包**（旁观模式看不到快捷栏）|
| 退出 | 聊天栏里可点的「[ 点击这里退出观战 ]」按钮，或输入 `/hub` |

## 9. 回主城的三条路（玩家其实有三条，别只记一条）

1. **右键「回主城」道具**（游戏内外都能用，最通用）
2. **右键等待室里的「返回大厅」道具**（红床）
3. **`/hub`** 命令（观战时也是这条）

三条路最终都走 `teleportToLobby`：清背包 → 给指南针 → 切生存 → 满血 → 回主城。

## 10. tab 列表

`HubManager` 定时刷新 header/footer：

- 每个**游戏一个分区**：`■ 游戏名 (人数)`，下面分 `[等待中]` 和 `[已加入]` 两行
- `tab.show-empty-games: false` 时，0 人的分区不显示（当前配置是 **false**）
- 玩家自己的名字前缀：`&7名字`（大厅）/ `&e[等待中·游戏] 名字` / `&a[已加入·游戏] 名字`

## 11. 头衔

菜单里有「头衔菜单」→ `cmd:titles`，也可以用 `/titles`（PlayerTitles 插件）。

## 12. 我们重构之后，玩家可见的变化

| 变化 | 状态 |
| --- | --- |
| 指南针 → 菜单 → 点游戏：**已房间化的游戏会先进"选房间"界面**（第一格创建新房间 + 8 格现有房间），没有地图登记的游戏行为完全不变 | ✅ 已实现；⚠️ 入口要同时挂 `clickGame` 和 `joinArena`，2026-11-02 已修 |
| **房间条目显示：状态（准备中 / 游戏进行中）、人数、地图名、房间号**；**左键直接进房** | ✅ 2026-11-06（HubCore 1.30.0）|
| **创建房间 = 先选"地图"再建**（地图可含多个世界，见 §12.1）| ✅ 2026-11-06（HubCore 1.30.0）|
| 大厅「开始/停止/删除」管理页：**只对 `hub.admin` 开放**（右键房间），普通玩家看不到 | ✅ 2026-11-06 |
| 进入房间会自动执行该游戏的 `join-command`（否则玩家站在房间里游戏不知道他来了）| ✅ 已实现 |
| 300s + 主持人机制（D21）| ⬜ 未实施（上游已同意）|
| 模板一律不加载，设计者 `/gw tp` 才进图 | ✅ 已实现（D19）|

**还没有动、但玩家看得见的**：观战、tab 分区、头衔、主城菜单里的 OP 编辑功能 —— 重构时**不要顺手改掉**。

### 12.1 房间化的界面流程（R3，玩家视角）

```
房间列表页（9×3，第一格永远是"创建新房间"）
   │   其余 8 格 = 现有房间，悬停显示：状态 / 人数 / 地图名 / 房间号；**左键直接进房**
   ↓ 点第一格
选地图页（该游戏在 maps.yml 里登记的**所有地图**；一张地图可以横跨多个世界）
   ↓ 点某张图          ← **无论这个游戏只有一张图，都会经过这一步**
才开始创建房间：按地图复制它声明的每个世界 → 删世界身份 → 加载 → 套世界规则 → 注册区域
   ↓
自动传送进房间 + 执行该游戏的 join-command（否则游戏不知道玩家来了）
```

要点：

- **三个概念别混**（2026-11-06 澄清，之前 GUI 一直混着用）：

  | 概念 | 是什么 | 存在哪 |
  | --- | --- | --- |
  | **地图 map** | 玩家眼里的"一张图"，**可以横跨多个世界**（派对就是 3 个） | `plugins/MiniGameLib/maps.yml` |
  | **模板世界 tmpl_** | 磁盘上的世界目录，是复制源 | `world/dimensions/minecraft/tmpl_*` |
  | **房间 room** | 一次运行实例：复制出的世界 + 一份游戏状态，键是 roomId | 内存 `RoomManager`，目录 `<roomId>_1`… |

  所以"选地图建房间"是 **map → room**；`tmpl_` 只是 map 内部的实现细节，**不该出现在玩家界面里**。

- **没有"只有一张图就跳过选图"的捷径**（用户明确要求）——选图是一次显式动作，
  以后加图也不需要改流程。
- 建房间的**初始化工作与 `/gw create room` 完全同一套代码**（都走 `RoomManager.createAsync` 的
  复制→身份清理→加载→规则→区域注册），GUI 只是它的一个入口。
- 房间列表页的其余 8 格只在**确实有房间**时才出现（D10），没房间就是空的。
- 点已有房间 → 房间动作页（进入并加入 / 开始 / 停止 / 删除）。
