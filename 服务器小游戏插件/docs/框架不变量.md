# 框架不变量

> 本文是重构的**验收基线**。写法参照 `nonebot-plugin-shitbot/docs/命令框架.md` 的「1.4 框架不变量」：
> 先把"任何时刻都必须成立"的谓词写出来，再让实现去满足它。

## 0. 速查

| # | 不变量 | 一句话 | 违反时的玩家感受 |
| --- | --- | --- | --- |
| **I1** | 玩家归属是一条链 | 玩家不能同时属于两个**并列**对局；但可以嵌套（派对 ⊃ 当前小游戏） | `/hub` 退出后又被拉回去；幽灵对局；主城刷屏 |
| **I2** | 区域归属单射 | 一块区域（整个世界，或世界内的一块）同时只属于一个对局；没人认领的是公共区 | 两个人开同一场；别人的规则盖掉我的；天坑把大厅的 PvP 也关了 |
| **I3** | 事件裁决唯一 | 一条事件同时只有一个"说了算的人"（= 受害者所在区域的归属者） | 打不掉血；爆炸不推人；本地能击飞面板不能 |
| **I4** | 生命周期唯一出口 | 对局只能由 `end(reason)` 结束，并向子对局递归传播 | `/hub` 退不掉；一局结束人没走干净 |
| **I5** | 状态转移封闭 | 状态只能按写死的转移表变化 | 重复开局；双倍积分；残留计分板 |

派生硬规则（不变量本身没法自我保证，靠这四条工程约束兜底）：

| # | 规则 | 一句话 |
| --- | --- | --- |
| **R1** | 单一事实源 | 一个游戏的定义只存在一处，其余全部派生 |
| **R2** | 单一写者 | 每份持久化数据只有一个写入者 |
| **R3** | 失败可见 | 框架不吞异常，被吞的要能被查 |
| **R4** | 契约一致 | 每个游戏 jar 声明契约版本，不匹配拒绝加载 |

## 1. 五条核心不变量

### I1　玩家归属是一条链（可嵌套）

**陈述**

> 任意时刻，对任意在线玩家 `p`，`p` 的归属构成一条**唯一的祖先链**：
> `root ⊃ … ⊃ leaf`（长度可为 0，表示在公共区/大厅）。
>
> 换句话说：**不允许出现"兄弟"关系** —— 玩家不可能同时属于两个并列的对局；
> 但**允许嵌套** —— 一个对局可以是另一个对局的子对局。

形式化：

```
∀ p ∈ Online :
    Owners(p) 构成一条链（任意两个元素互为祖先或后代）
  且 | leaf(p) | ≤ 1
```

**为什么是"树"而不是"至多一个"**

因为「街机派对」这种模式天然是嵌套的：

```
派对 session（根）
   ├─ 第 1 局：烫手山芋 session
   ├─ 第 2 局：雪塔大作战 session
   └─ 第 N 局：……
```

玩家在玩"烫手山芋"时，他**同时**属于「派对」和「烫手山芋这一局」。
如果把 I1 写成"至多一个"，这个合法形态就表达不出来了。

> 这个修正是由上游对派对流程的描述直接推出的：
> 「传送至等待室（颁奖室）→ 有人点开始 → 随机抽一个小游戏大家一起玩 → 玩完再随机一个 → 重复几次 → 统计总星数 → 送上颁奖台」。
> 结构上就是一个 session 里嵌了 N 个**不同游戏**的子 session。

**嵌套是可选的，不是必须的**：玩家也可以**单开一把小游戏**，不经派对。
所以链的长度只有两种合法形态：

```
单开：  [烫手山芋#41]                    ← 链长 1，自己就是根
派对：  [派对#3] ⊃ [烫手山芋#41]         ← 链长 2，父是编排器
大厅：  []                              ← 链长 0
```

**唯一的判定规则**：链上不能有并列。至于是"不装派对直接开一局"还是"派对里开一局"，
对 I1 来说没有区别 —— 框架不关心根是谁，只关心"有没有并列"。

**这和你文档 3.6「子任务与嵌套命令」是同一个模型**：嵌套命令挂在 `_inner_cmds` 里，
`unlock()` 递归解锁。这里对应：`end(reason)` **向所有子 session 递归传播**。

**它禁止什么**

- 同一个 `UUID` 同时出现在两个**并列**插件各自的 `Set<UUID>` 里；
- 玩家同时收到两个并列对局的侧边栏 / 计分板 / 倒计时 title；
- 玩家"A 游戏已经结束，但 B 游戏仍认为他在场"；
- 子对局结束后，父对局不知道（链断裂）——所以传播必须是双向的：子 `end` 要通知父，父 `end` 要杀子。

**它对应的真实事故**

| 事故 | 现在的成因 |
| --- | --- |
| `/hub` 中途退出，过一会儿又被拉进下一局 | `ArcadeParty` 把玩家留在 `playing` 集合里（详见 §3）；且派对与当前小游戏之间**没有父子关系**，退出信号传不下去 |
| 玩雪塔时后台刷 `IllegalArgumentException: Cannot measure distance between minecraft:overworld 和 minecraft:world_tr` | 某插件在自己的 `PlayerMoveEvent` 里把玩家跨世界传送，后面注册的监听器拿新旧世界坐标比距离 |
| 进服时连刷 N 行"你不在任何场中"（N = 注册了 lobby handler 的插件数） | 回主城广播给所有插件，每个插件都以为自己有一份该玩家状态 |

**怎么测**

随机执行 `join / leave / /hub / 换世界 / 退服 / 重登 / 派对中途退出` 序列，**每一步之后**断言：
1. 归属集合构成一条链（无并列）；
2. 链上每一层的 `state` 自洽（父 `RUNNING` 时子不能是 `CREATED`）。

违反时打印 `[I1] 玩家 X 的归属不是链：[party#3, skypit#12]`。

**靠什么保证（结构，不是自觉）**

- 归属只能通过 `PlayerSession.attach(session, parent)` / `detach(reason)` 修改，二者在 runtime 内部；
- `attach` 时若已有归属且新 session **不是**现有叶子的后代 → **抛异常**，不静默覆盖；
- 子 session 的 `end` 自动向父上报 `ROUND_END`；父的 `end` 递归 `detach` 所有子；
- 游戏插件拿不到"我的参与集合"，只能查询"我现在属于谁 / 我的根是谁"。

### I2　区域归属单射（粒度到"区域"，不只是"世界"）

**陈述**

> 「**区域**」= 一个世界，或世界内的一个包围盒/多边形。
>
> 任意时刻，每个区域满足 `|{ s : s.owns(region) }| ≤ 1`。
> **未被任何 session 认领的区域 = 公共区**，归 hub 规则。

形式化：

```
∀ r ∈ Regions :  |Owners(r)| ≤ 1
Owners(r) = ∅  ⟹  r 是公共区
```

**为什么粒度必须到"区域"**

因为场地不一定独占整个世界，而且**这是本项目的主要形态，不是例外**。实测线上配置：

| 事实 | 数据 |
| --- | --- |
| `world_mini_game` 在插件配置里出现 | **1200 次** |
| 引用它的插件 | **14 个**（AnimalSlaughter / AnvilBattle / ArcadeParty / DigToBottom / GroupRace / HillKing / JumpFill / KnockbackBattle / LandClaim / MemoryFlip / OneShot / SnakeParty / TNTBattle …） |
| 分布 | 各自在世界的不同坐标上"搭"自己的场地，互不相邻 |

举几块实际坐标（都在 `world_mini_game` 里，Y 也各不相同）：

| 游戏 | 中心 / 范围 | 形状 |
| --- | --- | --- |
| HillKing | (627, 53, 307) r=7 | 圆 |
| LandClaim | (20, −14, −207) r=10 | 圆 |
| SnakeParty | (258, 34, 296) r=60 | 圆 |
| TNTBattle | (191..334, 57, −32..101) | AABB |
| JumpFill | (18..26, 0, 18..26) | AABB |
| AnimalSlaughter | (12, 50, 301) 附近 | 圆 |
| ArcadeParty | (−262..−249, 51..57, 589..599) | 等待室 + 颁奖台 |

也就是说：**`world_mini_game` 是一个 14 个租户共用的世界**，谁都不能对这个世界整体做决定
（改 gamerule、全服爆炸保护、区块卸载、实体扫描）。只写"世界归属"时这种情况完全表达不出来 ——
而它恰恰是最刺眼的那条。

把粒度降到区域之后，**"天坑"和"大厅"是同级的两个区域**，各自有归属者，谁都不能替对方做决定。

**关键补充：区域归属是"加载期静态声明"的，不是运行时抢的**

> 每个插件在加载期声明自己占用的区域列表（世界 + 形状）。
> 框架在这一刻就做冲突检测；冲突 → **启动失败并打印冲突表**。
> 运行时 session 只是在"已经归我的区域"上开/关，不存在抢占。

理由：动态 claim 会引入"谁先抢到"的竞态，又退回优先级战争。
静态声明让 I2 在**启动那一刻就可以判定**（T2），不需要等运行时。

**现状的障碍：区域边界现在根本无法机读**

要做静态声明，得先把"这块地多大"变成机器可读的。而现在的存储方式至少有三种、互不兼容：

| 插件 | 存法 |
| --- | --- |
| HillKing / LandClaim / SnakeParty | `center:` + `radius:` → 圆 |
| TNTBattle | `pos1:` + `pos2:` → AABB |
| JumpFill | `water-pos1` / `water-pos2`（而且这只是水池，不是整个场地） |
| 多数游戏 | 只有 `spawns:` 出生点列表，**没有边界** |

**所以现在连《区域归属表》都生成不出来** —— 这本身就是 R1（单一事实源）必须覆盖"区域"的理由：
不只是名字要单一来源，**区域的几何定义也要单一来源**。

**它禁止什么**

- 两个对局同时在同一场地开局（互相清场、互相结算）；
- 两个插件同时改同一区域的 gamerule / 时间 / 天气 / 方块；
- **一个区域的所有者对"别人区域"里的事件下判断**（← 天坑的真正病灶，见下）。

**它对应的真实事故**

| 事故 | 现在的成因 |
| --- | --- |
| BuildRun 建造阶段在 `world_gtb` 里被 GTB 的方块保护拦住 | 两个游戏**共用**世界，且都没声明"我只管这一块" |
| 幸运之柱死亡不掉落、地上没掉落物 | `keepInventory` 是世界级 gamerule，被另一个游戏的设定盖住 |
| **全服玩家互伤被禁止，`world_lp` 的 `pvp: true` 失效** | 天坑的 PvP 守卫**替不归它管的区域做了决定** |

**天坑为什么会同时踩到 I2 和 I3**

源码（`SkyPitListener#onDamageGuard`）写的是：

```java
if (!inPit(victim) || !inPit(attacker)) event.setCancelled(true);   // 不在我这里 → 禁止
```

这是一个**全域否定**：「凡是不属于我的地方，我都替你们做决定」。
正确写法是**局部肯定**：「在**我的区域**内，我允许 PvP」。

```
错误（全服否定）：∀x ∉ pit  ⟹  禁止
正确（自己区域）：∀x ∈ pit   ⟹  允许；其余一律不表态
```

但"其余不表态"之后，**谁来兜底拒绝？** 必须是框架，不能是某个插件 ——
这就是 I3 的作用：默认拒绝由框架统一执行，游戏只在自己的区域内做"允许"。

所以修好 I2 之后这种代码在结构上就写不出来了：游戏插件拿不到全局事件注册口，
它只能在自己的 `region` 内回答 `canDamage(a, b)`。

**声明机制（已落地，2026-10-31）**

`MiniGameLib` 新增两个类：

- `com.hub.region.ArenaRegion`：一块地盘的不可变声明（`gameKey` + `arenaName` + `world` + AABB 六坐标）。
  构造时自动把两个对角点归一化成 min/max，所以用户随手点两个角（`y1 > y2`、`z1 > z2`）也不会错。
  提供两种工厂：`box(a, b)`（两个 `Location`，内部就是拆成 6 个坐标，与 9 参数构造完全等价，
  额外做「两点必须同世界」校验）与 `around(center, radius, height)`（中心+半径 → **推导**外接 AABB）。
  区别只在"边界已知 / 需要推导"以及"世界要不要已加载"——前者要求 `Location` 绑着已加载的世界，
  9 参数构造只吃世界名。
- `com.hub.region.RegionRegistry`：登记 + 两两重叠检测 + 启动汇总。
  **不抢占**：同一 `gameKey+arenaName+world` 再注册就是覆盖（重载友好）；
  游戏 `onDisable` 调 `unregisterGame` 撤销，避免 `/reload` 后留幽灵区域。

冲突分两级：`CROSS_GAME`（不同游戏的地盘重叠，会互相踩，WARNING）与
`SAME_GAME`（同一游戏两块场地重叠，多半是建场手滑）。
当前**只报警不阻断启动** —— 因为 21 个游戏还没迁完，直接拒绝启动会把服务器搞挂；
等全部迁完再升级成"冲突即拒绝启动"。

接入方式见 `HubCore/docs/游戏插件接入指南.md` 第 4 步。

**实测证据：主城的 PvP 政策现在由一个小游戏插件实现（归属倒置）**

`/hub doctor` 打印的第一个世界就是 `world`（主城）：

```
- world pvp=true keepInventory=true
```

从**未经修改的原样副本**里解 `world/dimensions/minecraft/overworld/data/minecraft/game_rules.dat`
也确认 `minecraft:pvp = 1`。也就是说 `server.properties` 的 `pvp=false` **并没有生效在主城**——
它只决定新建世界的默认值，已存在的世界以存档里的 gamerule 为准。

于是「大厅里不能互殴」这件事，唯一实现是 **SkyPit 的 `onDamageGuard`**。
SkyPit 只是主城里的一块区域，却在替整个主城执行政策 —— 这是 I2（区域归属）与
I3（事件裁决唯一）同时被违反的样子。

正确形态：`world` 的公共区政策由 **HubCore**（主城的所有者）决定，
天坑那块 AABB 内的政策由 **SkyPit** 决定。要做到这点，必须先有区域声明（见下）。

**跨区规则（必须写死，否则又变成"看谁后跑"）**

> 裁决者 = **受害者所在区域**的归属者。
> 若攻击者不在同一归属者的区域内 → 视为跨区行为，**按公共区规则处理（默认拒绝）**。

这样"主城里互相打"永远 hub 说了算，"天坑里互相打"永远 SkyPit 说了算，
"天坑的人打主城的人"（传送竞态下会出现）默认拒绝。

**怎么测**

- 断言 `region → session` 映射是单射；
- 启动自检打印《区域归属表》：哪些世界/包围盒被谁 claim、哪些是公共区；
- 同一区域重复 claim → 第二个申请者**加载失败并明确报错**。

**靠什么保证**

- `RegionClaim` 由 runtime 授予，游戏只能"申请"，拿不到直接改 gamerule 的能力；
- 未 claim 的区域 = 公共区，**任何游戏都不许改规则**（只能读）。

### I3　事件裁决唯一

**陈述**

> 对任意一条被框架关注的事件 `e`（伤害 / 移动 / 破坏 / 放置 / 交互 / 死亡 / 重生 / 聊天 …），
> `|{ v : v.decides(e) }| ≤ 1`。
> 该 `v` 是 `e` 发生位置 / 涉及的玩家的**归属者**；无归属时归"公共区规则"。

**它禁止什么**

- N 个插件在 4 个优先级上互相 `cancel()` / `setCancelled(false)`；
- 游戏插件自己 `registerEvents(...)` 注册全局监听器；
- "谁后注册谁赢"这种依赖平台的顺序。

**它对应的真实事故**

| 事故 | 现在的成因（源码） |
| --- | --- |
| 全服玩家互伤被禁止，`world_lp` 的 `pvp: true` 失效 | `SkyPitListener#onDamageGuard`（LOWEST）只要双方不在天坑就 `setCancelled(true)`，**不看世界、不看别的游戏** |
| 单挑的风弹推不动人 | GuessTheBuild 在 HIGHEST 无条件取消**所有世界**的爆炸 |
| 本地能击飞、面板不能 | 同优先级下按插件注册顺序调用，Windows/Linux 的 jar 读取顺序不同 |

**量化现状**：全仓库 **308 个 `@EventHandler`**，其中 **133 个（43%）在 `HIGHEST`** ——
这就是"优先级战争"的指纹。重构目标：**游戏模块里 0 个**。

**怎么测**

- 静态：游戏模块出现 `@EventHandler` → CI 直接失败；
- 运行时：每次裁决写一条审计（`事件 / 归属者 / 结果`），断言同一事件只有一条裁决。

**靠什么保证**

- 游戏插件**拿不到** `PluginManager#registerEvents` 的入口（api 层不暴露）；
- 游戏只实现 `scope.canDamage(a, b)` 这类**纯查询**，由框架统一裁决；
- 默认拒绝，显式允许（现在是默认放行、大家乱取消）。

### I4　生命周期唯一出口

**陈述**

> 一个 `GameSession` 离开 `ENDED` 之前的最后一次状态变更，**必须**是 `end(reason)`；
> `reason` 必填，取值：
> `ROUND_END` / `PLAYER_QUIT` / `ADMIN_STOP` / `ABORT` / `ERROR`。
>
> 并且：
> 1. **"把玩家送回大厅"不改变任何归属**；
> 2. `end` 必须**向所有子 session 递归传播**（对应 I1 的树形归属）。

**它禁止什么**

- 用 `teleportToLobby` 同时表达"这一局结束了"和"我要退出"；
- 每个插件自己起 `BukkitTask` 收场、自己 `onDisable` 写盘；
- 一个对局被 `end` 两次（重复结算），或者一次都没 `end`（幽灵对局）；
- 父 session 结束了但子 session 还在跑（派对散了，小游戏还在计分）。

**它对应的真实事故（这是 §3 详解的那个）**

`/hub` 中途退出 → 因为 `teleportToLobby` 的两种语义无法区分，
ArcadeParty 选择"对局中不当成退出" → 玩家留在 `playing` → 过渡阶段
`p.performCommand(join)` 又把人拉回场地。

**嵌套场景下的语义（派对就是这种）**

```
玩家 /hub
  └─ 派对 session.end(PLAYER_QUIT)
       ├─ 当前小游戏 session.end(PLAYER_QUIT)   ← 递归
       ├─ 取消过渡倒计时任务
       ├─ 该玩家的星数按"中途退出"处理（不是 ROUND_END）
       └─ 从玩家人数里减 1；若人走空 → end(ABORT)
```

现在的代码做不到这件事，因为**派对和当前小游戏之间没有父子关系** ——
派对只知道 `performCommand("hill join")` 发出去了，不知道那个游戏开了没、结束没。

**怎么测**

- 断言每个 session 在整个测试中**恰好** `end` 一次（父、子分别计数）；
- 断言 `/hub` 之后立刻 `player.session == null`（而不是"还挂着但人不在"）；
- 断言子 session 先于父 session 结束，且父收到过子的 `ROUND_END`；
- 断言不同 `reason` 导致的收场动作不同（`ROUND_END` 保留统计、`PLAYER_QUIT` 给退出提示、`ABORT` 不记成绩）。

**靠什么保证**

- `end(reason)` 是 api 上**唯一**能从 `RUNNING` 出来的方法（没有 `stop()` / `finish()` / `setState()`）；
- `teleportToLobby` 从 api 上**移除**，改为 `hub.sendToLobby(player)`，语义只有"传送"；
- 所有 `BukkitTask` 由 session 持有，`end` 时统一取消（对应你文档里的 `unlock()`）；
- 子 session 由父 session 创建（构造时绑定 parent），父 `end` 时自动递归 —— 参考你文档 3.6 的 `_inner_cmds` 递归 `unlock()`。

---

### I5　状态转移封闭

**陈述**

> `GameSession.state ∈ { CREATED, WAITING, RUNNING, ENDING, ENDED }`，
> 合法转移集合**写死在框架里**：

```
CREATED ──► WAITING ──► RUNNING ──► ENDING ──► ENDED
   │            │           │          │
   └────────────┴───────────┴──────────┴──► ABORTED（任何状态都可，但只能一次）
```

> 任何不在表里的转移 → **抛异常 + 记录**，不得静默忽略。

**它禁止什么**

- 重复 `start()`（现在靠各游戏自己 `if (state == RUNNING) return;`，漏一个就重复开局）；
- `ENDED` 之后还发计分板 / 还处理伤害 / 还累加分数；
- 结算两次（双倍积分、双份记录）。

**它对应的真实事故**

- 重复开局导致计时器叠加、双倍记分；
- 对局结束后侧边栏残留、玩家还能被判定为"在场"。

**怎么测**

- 状态转移表单测（每个非法转移一条用例，断言抛异常）；
- 随机事件序列（fuzz）后断言状态落在 `ENDED` 且 `end` 计数 == 1。

**靠什么保证**

- `state` 字段私有，只能经 `transition(to)` 修改；
- 每个转移点有 `guard`（对应你文档 3.4 的 `_guard_state()`），不满足就拒绝并给出原因。

## 2. 四条派生硬规则

### R1　单一事实源

**规则**：一个游戏的定义只存在一处（`GameKey` + 注册时声明），
菜单 / 场地子菜单 / 观战列表 / tab 分区 / 编排器**全部从它派生**。

**禁止**：

- 在 YAML 里把游戏名当键（`action: game:TNT大战` 这种）；
- 跨插件 `Bukkit.dispatchCommand`（"hill join" 这种字符串接口）；
- 启动后静默容忍悬空引用。

**为什么必须**：I2 / I3 的前提是"能判定谁是归属者"。如果同一个游戏有 4 个名字
（plugin.yml 显示名 / 注册表 id / 场地状态键 / 菜单 YAML），归属判定本身就没有权威，
不变量无从谈起。

**真实事故**：主菜单点「TNT大战」弹出空菜单，观战列表里却叫「TNT 对战」——
两套名字、零校验。（详见体检报告 §5.3）

**验收**：菜单引用了不存在的 `GameKey` → **启动失败并列出问题**，而不是静默给个空菜单。

---

### R2　单一写者

**规则**：每份持久化数据在同一时刻只有一个写入者。

| 数据 | 唯一写者 | 允许写入的时机 |
| --- | --- | --- |
| 对局数据（本局分数/轮次） | 该 `GameSession` | `RUNNING` 内 |
| 玩家累计记录（`players.yml` 的某个 namespace） | 该游戏的 `PlayerStore` 视图 | 只能"读盘→只替换自己那块→原子替换" |
| 世界数据（方块、gamerule） | 该世界的 `WorldClaim` 持有者 | claim 期间 |
| 插件配置（`config.yml`） | 只有运维 / 管理员命令 | **不得**在 `onDisable` 从内存回写 |

**为什么必须**：现在 6 个插件（`MurderMystery / SkyPit / TntRun / DuelArena / HotPotato / BuildRun`）
在 `onDisable` 用内存回写配置，"改线上配置"必须"先停服再覆盖"，
否则关服那一刻旧值盖回去 —— 这是"改了没生效"的头号原因。

**验收**：
- 断言 `players.yml` 任一 namespace 的数据不会因其他 namespace 写入而丢失；
- 断言配置回写只发生在 session `ENDED` 之后（且只写自己负责的段）；
- 删掉 `onDisable` 回写，改为"变更即写"。

---

### R3　失败可见

**规则**：框架不得吞异常；被捕获的异常必须带来源标识记录，并计入 `/minigame doctor`。

**禁止**：`catch (Exception ignored) { }`（全仓库多处，典型在 `notifyLobbyHandlers`）。

**为什么必须**：不变量被违反时，如果没人知道，就等于没有不变量。
现在的现象是"某个插件悄悄挂了 → 玩家看到的是游戏行为诡异 → 日志里什么都没有"。

**验收**：
- CI 检查 `catch (Exception ignored)` 的出现；
- `doctor` 输出最近 N 条被捕获的异常（含来源插件名、次数、最后发生时间）。

---

### R4　契约一致

**规则**：每个 game jar 在 `plugin.yml` 声明契约版本；core 校验，不匹配拒绝加载并报错。

```yaml
# minigame-game-*.jar 的 plugin.yml
minigame-contract: 1        # 框架契约版本
minigame-key: skypit        # 强类型身份的唯一来源
```

**为什么必须**：现在 26 个模块里 **22 个**的 `pom.xml` 版本 ≠ `plugin.yml` 版本，
ArcadeParty 更是 pom 1.3.1 / plugin.yml 1.3.3 / 线上 jar 1.3.5 三处各不同。
版本不可信 → "仓库能重建线上"这句话就不成立。

**验收**：契约不匹配 → 启动日志明确列出"哪个 jar / 期望版本 / 实际版本"，且该游戏不注册。

## 3. 四层强制（不变量靠什么落地）

| 层 | 手段 | 例子 |
| --- | --- | --- |
| **T1 编译期** | 接口上不让写 | 游戏模块拿不到 `registerEvents`；没有 `setState`；`end(reason)` 是唯一出口；`GameKey` 是值对象 |

| **T4 测试期** | 单测 + 冒烟 | 每条不变量至少一个测试；随机操作序列 fuzz |

**原则**：能不变量尽量靠 **T1** 保证（写不出来 > 检查出来），T2/T3/T4 只兜底。
