# 地图与房间的数据结构（重构设计稿）—— 2026-11-02

> 本文定的是**房间化的数据模型**，来自用户的两条纠正：
> ① **一个模板世界会被多个小游戏引用**，每个游戏对它的初始化不同；
> ② **一个小游戏房间可能需要多个房间世界**（派对：子游戏散落在 3 个世界里）。
>
> 现有实现（`WorldTemplate{gameKey, rules, regions}` + `Room{一个 world}`）**两者都不成立**，要重做。

---

## 1. 三个数据结构

### 1.1 `WorldTemplate` —— 只剩"一份世界目录"

```java
record WorldTemplate(String key, String folder, File dir, long bytes)
```

不再有 `gameKey` / `rules` / `regions`。模板**不属于任何游戏**，它只是容器。

### 1.2 `GameMap` —— 一张地图 = 一组世界实例 + 各世界的区域

```yaml
maps:
  arcadeparty:
    迷你小游戏派对:
      entry: { template: mini_game, x: 42, y: 38, z: 16 }   # 入口点（≠ 出生点）
      worlds:
        - template: mini_game
          rules: { pvp: false, fixed-time: 6000 }           # 世界级缺省
          regions:
            - name: 高台之王
              box: {x1: .., y1: .., z1: .., x2: .., y2: .., z2: ..}
              rules: { pvp: true }                          # 区域级覆盖
            - name: 蛇行
              box: {…}
        - template: pvp_mini_games
          regions: [ {name: 万箭齐发, box: {…}} ]
        - template: tr
          regions: [ {name: 雪塔, box: {…}} ]
  hillking:
    高台之王:
      worlds:
        - template: mini_game
          regions: [ {name: 高台之王, box: {…}} ]
```

**规则层级**：世界级 `rules` 是缺省，区域级 `rules` 覆盖（用户已拍板，暂时如此）。

**同一模板世界被多个游戏引用**：两个游戏各自在 `maps:` 下有自己的条目，指向同一个 `template`——
互不影响，各按自己的 `regions`/`rules` 初始化。

### 1.3 `Room` —— 房间是世界实例的集合，自己的名字与世界名解耦

```java
final class Room {
    String roomId;                // 房间名（不再是世界名）
    String game, map;
    List<WorldInstance> worlds;   // { templateKey, worldName }
    Location entry;               // /hub join 后玩家应出现的位置（入口点，不是出生点）
}
```

**入口点 ≠ 出生点**（用户拍板）：`entry` 由创建房间时按 `map.entry` 填写，只保证"进得来"。

**`Room.entry` 对游戏只读**（用户拍板，2026-11-02）：它是**框架给游戏提供的信息**，
不是游戏改自己状态的地方。游戏要记"这个玩家落在哪"，应存在**游戏自己的状态**里
（例如游戏内的 `Map<UUID, Location>`），不要往房间上写。

理由（R2 单一写者）：
- 房间这份数据的来源是**地图声明**，写者是**框架**；
- 游戏也能写的话，房间行为会变成"取决于最后一个跑过的游戏"，排障时这个值不可信。

实现：`private Location entry` + `entry()` 只读 + `setEntryOnce(...)`（建房时写一次，
重写会被忽略并告警）。

**同理（同一轮一起封的）**：
- `game` / `map`：`private` + 只读 getter，框架建房时写一次；
- `instances`：`private` + `instances()` 返回**不可变视图**，只有框架能加/清。
  这个最危险 —— 外部能 add 的话房间会凭空多出没复制过目录的世界实例，
  `/hub join`、区域归属、销毁回收全会错，而且是**静默**的。

## 2. 两个命令流程

### 2.1 `/hub create <game> <map>`

```
① 校验可行性（游戏已登记、地图存在、模板目录存在、容量/权限）
② map → 需要哪些世界（worlds[].template）
③ 对每个模板：以框架身份提权执行 /gw create room <template>，拿到 room 世界
④ 按 map 里该世界的 regions/rules 初始化各个世界（区域登记 I2 归属到 (roomId, game)）
⑤ 用 entry 填 Room.entry；登记 Room
```

### 2.2 `/hub join <房间名>`

```
① 校验（房间存在、玩家状态允许）
② 取 Room 数据（含 entry）
③ 框架内部把玩家放进 entry 所在世界（**不经 /gw tp 命令行**——它只到默认出生点，会错位）
④ 调用游戏侧 init(player, room)：最终出生点、装备、会话挂接、UI 全归游戏
```

`/gw tp <world> [x y z]` 保留为**运维手工用的原子能力**（可加可选坐标），`/hub join` 不调它。

## 3. map 的边界：只放数据，不放流程（用户拍板）

| 放 `map.yaml` | 留在游戏代码 `init` |
| --- | --- |
| 需要哪些世界实例 | 玩家进哪个世界、落在哪 |
| 每个世界的区域盒子与名字 | 发什么装备、什么游戏模式 |
| 世界级/区域级规则 | 生成实体/NPC/告示牌 |
| 入口点 | 会话挂接、广播、UI |

## 4. 迁移与验收

**数据迁移**（现有事实齐全：运行时区域声明 + 各游戏配置）：
把现在 23 个 `tmpl_<游戏>_<世界>` 模板改回"**按上游世界**"的少数模板，
再建 `maps:` 条目（游戏 × 地图 → 世界清单 + 区域 + 规则）。

**代码顺序**：`WorldTemplate` 瘦身 → `GameMap` 解析 → `Room` 多世界 → `/hub create` 新流程 →
区域登记改造 → `RoomBinding` 键改 `(roomId, game)` → `/hub join` 新流程。

**三个验收用例**（覆盖用户指出的两类情况）：
1. 单世界单游戏：hillking @ mini_game
2. **单世界多游戏**：G1/G2 共用同一个模板世界
3. **多世界单游戏**：派对（3 个世界）
